# MVP 后的竞赛功能增强建议

现有优势是三场景真实注入、HolmesGPT 诊断、LangGraph 审批恢复、白名单执行、独立探针和审计持久化。工作台已经有阶段轨迹、证据引用定位、轮次切换、审批和 Markdown 导出，不应将这些再次包装成新增能力。

建议定位：**基于多模态证据融合与安全闭环的 AIOps 多智能体故障诊断平台**。增强重点是证据如何进入诊断、Agent 如何根据证据改变下一步，以及如何客观证明收益。

## 建议优先级

| 顺序 | 增强切片 | 增量价值 | 初版估算 |
| --- | --- | --- | --- |
| 1 | F17 真实评测基座与盲诊输入隔离 | 证明模型依据证据诊断，保存正确、错误与拒答结果 | 4–7 |
| 2 | 多模态截图证据接入 | 让真实错误截图、监控截图成为可引用证据 | 3–5 |
| 3 | 候选根因与受限主动补采 | 展示排除假设和动态编排，而非固定顺序调用模型 | 3–5 |
| 4 | 服务影响图与事故复盘摘要 | 让评委快速理解故障位置、影响路径和恢复依据 | 2–3 |
| 5 | 连续健康窗口与复发提示 | 区分一次检查成功和一段时间内稳定恢复 | 1–2 |

新增能力的实现应在现有 P0 验收收口后推进；评测基座本身属于已有 F17。方案设计和附件接口契约可提前并行，不扩大执行器权限。

## 1. 先把“已知场景闭环”增强为“盲诊与客观评测”

当前 `Workflow.diagnose` 传入 `scenario_key`，EvidenceAgent 按场景选择日志、探针和专属 Runbook，Runbook 明写真实注入方式与根因。Planner 也直接收到当前场景的动作和目标。这是 MVP 的已知场景安全闭环设计，但不能直接用来证明未知根因定位能力。

新增盲诊入口：模型只收到症状、正常服务关系和实际观测；注入场景、故障标签、预期答案保留在控制器及评测侧。不能只删除场景字段，却仍提供按答案筛选的 Runbook、文件名或目标日志。初版统一收集四个服务的受限观测，Runbook 提供通用排查知识或全部候选知识。

保存模型原始结论，包括错误和 UNKNOWN，由独立评测比对注入真值。现有执行器继续使用场景、实测前置条件、审批和动作白名单做安全门禁；盲诊不意味着扩大处置权限。诊断正确率统计与执行许可必须分开，不能只统计通过安全校验的诊断。

先完成 F17 的 3×3 真实闭环与异常验收，再增加相同证据快照下的对照：

- A：单次 HolmesGPT 诊断。
- B：多 Agent 诊断与复核，纯文本证据。
- C：相同流程，增加视觉证据。

纯诊断对照使用相同版本、初始证据和预算；端到端对照使用相同故障条件、工具权限、审批与验证规则，并披露额外采证次数。记录根因正确率、恢复成功率、错误处置提议及拦截、拒答情况、调用次数和耗时。模型时间、人工审批等待、启动与验证时间分开显示。token 未返回则标未知；费用需要实际 usage 与明确计价版本。

九次实验是复现基线，不足以证明广泛泛化或统计显著性。若多 Agent 只提高可解释性而增加耗时，也应保留这个结果。

代码落点：`backend/app/graph/workflow.py`、`backend/app/agents/evidence.py`、`backend/app/integrations/models.py`、独立 evaluation service/API/持久化与前端评测页。

## 2. 通义千问作为视觉证据适配器

第一版聚焦用户上传的真实错误页面和运维截图。后台调用账号实际可用的千问视觉模型，输出结构化观测，再由 HolmesGPT 与日志、探针联合分析。保留 HolmesGPT 的诊断职责和 LangGraph 的主状态机。

每份视觉证据保存原图引用、哈希、来源、上传时间、图中可识别的观测时间、提取文本、异常区域、模型版本与不确定项。上传时间不能代替截图实际发生时间。展示时区分图上直接观察与模型推断；点击诊断引用能回到图片区域。区域坐标需依据实际模型版本归一化并检查边界。

优先验收三种情形：清晰截图能正确提取；模糊或缺时间截图明确不确定；历史截图显示异常而当前探针健康时，提示时间或证据冲突并补查，不能直接触发恢复。

若监控图已有结构化原始数据，优先使用原始数据；视觉服务于没有接口的异构证据入口。把同一批日志画成图再识图，不能算独立证据。图片理解支持图像问答和区域定位，也不意味着能精确还原所有曲线数值或可靠证明因果。

附件第一版仅接受经验证的有限图片格式和大小，使用后台受控存储与模型请求；密钥由运行环境注入。截图中的指令作为不可信数据，不能成为工具或执行参数。图片本身不决定修复 PASS。

代码落点：新增 `integrations/vision.py` 与附件服务，扩展 Evidence 的附件元信息、EvidencePanel/DetailDrawer 和工作台上传入口。现有通用 Evidence 结构及审计可复用，不需要另加一套工作流框架。

## 3. 候选根因、反证与主动补采

诊断输出增加少量候选根因、各自支持与反对证据、缺失检查。缺证据时，模型只能从注册的检查 ID 中选择，Graph 调用固定探针或日志读取，再返回诊断；补采最多一到两次，设置总耗时预算。

演示可以从“代理返回 502”开始：核查代理、直连应用、容器状态和日志，逐步确认上游应用停止。对于不支持的故障，给出 OTHER/UNKNOWN 与人工处理建议；仅在已有白名单场景内进入恢复审批。现有三场景之外的真实注入和新动作属于后续独立需求。

页面显示“为什么需要这项检查”和“新增证据排除了什么”。展示可核对的结论摘要与证据，不展示模型隐藏思考过程。模型自报 confidence 不能当作经过校准的成功概率。

## 4. 可点证据的服务影响图与复盘摘要

使用明确配置的真实业务关系构建四服务图，叠加探针、日志和诊断依据。启动依赖不能直接等同于业务因果关系：当前 MySQL 故障影响 `/db-check`，并不意味着独立的 `/api/hello` 同样失败。区分已观测异常、配置依赖与推断传播。

复盘摘要从持久化记录生成：何时发生、影响哪个接口、根因及引用、批准动作、修复前后探针、未解决项，保留原审计附录。若后续增加时间回放，只投影历史记录，不重新执行 Docker 动作；明确这是历史回放而非现场运行。

## 5. 稳定恢复验证

当前 `Probes.verify` 在一次完整采样 PASS 后即可结束。可以提供可配置的连续健康次数和观察窗口，保存每次实测，出现再次失败时显示恢复不稳定。观察窗口中的暂时未知与明确失败应按单独规则呈现；不能删除失败采样，也不能把窗口内健康宣称为永久不复发。

## 首个建议交付切片

先实现 **F17 评测基座 + 隐藏答案的三场景盲诊**：保留原闭环入口，新增不透露场景的模型输入构造、全域受限观测、独立正确率记录和真实评测页面。验收后接入“上传 502 截图 → 视觉症状提取 → 真实补查 → 根因引用 → 审批 → 真实复测”的演示链。

后续的视觉与动态补采必须各自有对照实验；不预先承诺它们一定提高准确率。
