## 一、先说结论：为什么「接上模型 key」不是第一步

《功能增强建议.md》第 21 行的判断，核对代码后完全成立，而且比原文更严重。

### 已经证明的（可以对外讲）

| 结论 | 证据 |
| --- | --- |
| 故障是真实发生的 | `docker compose stop` 真实停止容器，独立用原生 docker 交叉核实 |
| 证据是真实的 | 容器状态、双探针、真实服务日志、Runbook |
| 动作受白名单约束 | `backend/app/services/executor.py:13-18` |
| 恢复结果由独立探针裁决 | `backend/app/integrations/probes.py:13-21` |
| 模型失败不伪造成功 | 无凭据时如实 `AI_UNAVAILABLE`，证据保留、诊断为空 |
| 审批与计划绑定 | `plan_id` 不匹配即 `BLOCKED` |

### 尚未证明的（**不能对外声称**）

**当前闭环无法证明模型具备根因定位能力。** 原因是模型在作答前就已经知道答案。
更准确地说：模型**即使完全不看证据**，也能答对——因为答案被硬编码进了它的输入与输出契约。

这直接决定了：接上模型 key 只能证明「模型能被调通」，不能证明「多 Agent 架构有价值」。
比赛评委如果追问「你怎么知道它是诊断出来的，而不是被告知的」，当前代码答不上来。

## 二、问题定位：答案在四处泄露

这是本轮新做的一次完整审计，比《功能增强建议.md》点出的三处多一处。

### 泄露点 1｜诊断上下文直接携带场景标识

`backend/app/graph/workflow.py:182` 把 `scenario_key` 放进诊断上下文：

```python
"scenario_key": state.get("scenario_key", "MYSQL_DOWN"),
```

### 泄露点 2｜采集阶段按场景挑证据，且 Runbook 明写答案

`backend/app/agents/evidence.py:30-53`：

```python
definition = SCENARIOS[scenario]
for service in definition.logs:          # 只取本场景相关服务的日志
    ...
path = ROOT / f"knowledge/runbooks/{definition.runbook}.md"   # 场景专属 Runbook
```

而 `knowledge/runbooks/mysql.md` 第 5 行白纸黑字写着：

> 故障现象：容器退出，认证连接的 SELECT 1 明确失败，demo-app /db-check 返回 503。

**即使删掉 `scenario_key`，Runbook 的文件名和内容依然泄露。** 这是《功能增强建议.md》第 23 行特别强调的：

> 不能只删除场景字段，却仍提供按答案筛选的 Runbook、文件名或目标日志。

### 泄露点 3｜规划器直接收到注册动作与目标

`backend/app/integrations/models.py:132-134`：

```python
"allowed_action": definition.action,
"target": definition.target,
"expected_checks": list(definition.checks),
```

Planner 不需要推理，只需要从给定选项里挑一个。

### 泄露点 4｜输出契约本身就是答案集（**本文档新发现**）

`backend/app/schemas/domain.py:83-89`：

```python
root_cause: Literal[
    "MYSQL_SERVICE_STOPPED",
    "REDIS_SERVICE_STOPPED",
    "UPSTREAM_APP_STOPPED",
    "INSUFFICIENT_EVIDENCE",
    "OTHER",
]
```

`HolmesDiagnosisProvider.diagnose` 用 `response_format(Diagnosis, ...)` 把这个 Schema 原样送进提示词
（`backend/app/integrations/models.py:69`）。**模型看到的 JSON Schema 里就列着三个场景的根因常量**，
其中每个都直接对应一个场景。

同时 `backend/app/agents/evidence.py:97` 与 `backend/app/services/executor.py:13-16` 强制
「根因必须等于注册值」「动作必须等于注册动作」—— 于是模型答错就直接被拦，
**当前闭环中不存在「模型判断错误」这个观测结果**，错误率恒为 0（通过安全校验的口径下）。

> 这一点必须写进设计：盲诊下 Schema 需要一套**不枚举场景根因**的契约，
> 否则换了输入隔离方式，提示词里仍然带着答案。

### 泄露点汇总

| # | 位置 | 泄露内容 | 盲诊下的处理 |
| --- | --- | --- | --- |
| 1 | `workflow.py:182` | `scenario_key` | 不传入 |
| 2 | `evidence.py:30-53` | 场景专属日志与 Runbook | 全域受限观测 + 通用排查知识 |
| 3 | `models.py:132-134` | 注册动作、目标、探针 | 只给症状与正常服务关系 |
| 4 | `domain.py:83-89` | 根因枚举即答案集 | 盲诊专用 Schema，根因用自由文本或症状描述 |

## 五、阶段 1｜评测基座 F17（4–7 人天）

《功能增强建议.md》第 11、37 行提到的 F17，在当前代码里**没有任何落点**
（`grep -rn "F17"` 只在文档中命中），需要从零建。

### 5.1 核心设计约束

1. **诊断正确率统计与执行许可必须分开。** 盲诊阶段允许模型答错，答错的记录必须被完整保存，
   而不是被 `validate_diagnosis` 拦掉后就消失。
2. **保存模型原始结论**，包括错误与 `UNKNOWN`，由独立评测侧比对注入真值。
3. **执行许可继续走现有安全门禁。** 盲诊不扩大处置权限——动作白名单、审批、探针裁决照旧。
   盲诊只是把「模型说���」和「平台允许做」拆成两件事。
4. **评测数据与工单数据分表。** 工单表 `incidents.detail` 带场景信息，混用会导致真值泄漏到评测记录里。

### 5.2 数据模型（建议）

新增 `backend/app/repositories/evaluation.py`：

```python
class EvaluationCase(Base):
    """一次注入条件。真值只存在于本表，评测侧以外不可见。"""
    __tablename__ = "evaluation_cases"
    id: str                # 条件 ID，同一条件被 A/B/C 三个变体复用
    scenario_key: str      # ← 真值，仅评测侧可见
    injected_at: str
    baseline: dict         # 注入前基线快照
    truth: dict            # 期望根因、期望目标、期望探针

class EvaluationRun(Base):
    """一次模型调用及其结果。"""
    __tablename__ = "evaluation_runs"
    id: str
    case_id: str
    variant: str           # "A" 单次 Holmes / "B" 多 Agent 纯文本 / "C" 加视觉
    mode: str              # "REAL" | "TEST/MOCK"
    evidence_snapshot: dict # 冻结的证据快照（对照组必须完全相同）
    model_config: dict     # 模型标识、版本、prompt 版本、JSON 模式
    budget: dict           # 调用次数上限、总耗时预算
    conclusion: dict       # 模型原始结论，允许错误与 UNKNOWN
    metrics: dict          # 根因是否正确、是否拒答、耗时、调用次数、token
```

**数据库迁移**：`backend/app/repositories/store.py:70-75` 目前硬校验 `user_version ∈ {0,1}`，
新增表必须按 README「增量升级需显式迁移」的要求升到 `user_version=2` 并写显式迁移，
**不能靠 `create_all` 静默补表**。

## 七、阶段 3｜对照实验（3–5 人天）

### 7.1 三组对照定义

| 组 | 定义 | 用途 |
| --- | --- | --- |
| A | 单次 HolmesGPT 诊断 | 基线：单模型单次调用能到多少 |
| B | 多 Agent 诊断与复核，纯文本证据 | 证明多 Agent 编排本身是否带来增益 |
| C | 相同流程 + 视觉证据 | 证明视觉证据的边际价值 |

**《功能增强建议.md》第 33 行的公平性约束必须写进实现**：

- 纯诊断对照：**相同模型版本、相同初始证据、相同预算**
- 端到端对照：**相同故障条件、相同工具权限、相同审批与验证规则**，并披露额外采证次数
- 模型时间、人工审批等待、启动时间、验证时间**分开统计**
- token 未返回则标未知；费用需要实际 usage 与明确计价版本

### 7.2 指标定义（建议口径）

| 指标 | 定义 | 注意 |
| --- | --- | --- |
| 根因正确率 | 结论与真值一致的比例 | **分母是全部运行，含错误与拒答**，不能只算通过安全校验的 |
| 恢复成功率 | 独立复测 PASS 的比例 | 与正确率分开报告 |
| 错误处置提议数 | 提议了错误动作且被拦截的次数 | 白名单拦截能力指标 |
| 拒答率 | 主动给出 `INSUFFICIENT_EVIDENCE` / `OTHER` 的比例 | 过高过低都要能解释 |
| 额外采证次数 | B/C 相对 A 多出的观测调用 | 增益是否值得额外开销 |
| 端到端耗时 | 分段：模型 / 人工等待 / 执行 / 验证 | 人工等待要单独列 |

> 第 35 行的一条提醒要写进报告：**九次实验是复现基线，不足以证明广泛泛化或统计显著性**。
> 若多 Agent 只提高可解释性而增加耗时，**也应保留这个结果**，不要筛掉。

## 八、阶段 4｜视觉证据与主动补采（条件触发，不阻塞前三阶段）

### 8.1 视觉证据（切片 2）

- 新增 `backend/app/integrations/vision.py` + 附件服务
- 每份视觉证据保存：原图引用、哈希、来源、上传时间、**图中可识别的观测时间**、提取文本、异常区域、模型版本、不确定项
- **上传时间不能代替截图实际发生时间**
- 展示时区分「图上直接观察」与「模型推断」
- 截图中的指令作为不可信数据，**不能成为工具或执行参数**；图片本身**不决定修复 PASS**
- 优先级规则：监控图已有结构化原始数据时**优先用原始数据**；
  **把同一批日志画成图再识图，不算独立证据**

优先验收三种情形（文档第 45 行）：清晰截图正确提取 / 模糊或缺时间截图明确不确定 /
历史截图异常但当前探针健康时提示时间或证据冲突并补查，**不能直接触发恢复**。

### 8.2 候选根因与受限主动补采（切片 3）

- 诊断输出增加少量候选根因、各自支持与反对证据、缺失检查
- 缺证据时模型只能从**注册的检查 ID** 中选择，Graph 调用固定探针或日志读取
- 补采最多 1–2 次，设总耗时预算
- 页面显示「为什么需要这项检查」「新增证据排除了什么」
- **不展示模型隐藏思考过程**；模型自报 `confidence` 不能当作经过校准的成功概率

### 8.3 服务影响图与稳定恢复（切片 4、5）

- 影响图用**明确配置的真实业务关系**构建；**启动依赖 ≠ 业务因果关系**
  （MySQL 故障影响 `/db-check`，不代表独立的 `/api/hello` 同样失败）
- 区分「已观测异常」「配置依赖」「推断传播」
- 稳定恢复：`Probes.verify` 目前一次 PASS 即结束（`backend/app/integrations/probes.py:157`），
  改为可配置的连续健康次数与观察窗口；**不能删除失败采样**，也不能把窗口内健康宣称为永久不复发

## 九、前端评测页（新增）

## 十一、明确不做的事

沿用《功能清单.md》第 64–68 行的边界，并补充本轮新增的：

- 不接入真实生产服务器，不让 AI 执行任意 Shell
- 不扩大执行器权限：盲诊、视觉、主动补采**都不新增可执行动作**，动作白名单保持三个固定项
- 不新增工作流框架：复用现有 LangGraph 主状态机与通用 `Evidence` 结构
- 不把视觉当作唯一证据入口：有结构化原始数据时优先用原始数据
- 不预先承诺视觉或动态补采一定提高准确率——**没有对照组就不写收益结论**
