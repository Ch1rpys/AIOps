# 面向 IT 运维的多智能体故障诊断与处置验证平台

> 最初范围是三种故障、五个页面。当前主系统已扩展为：**故障编译器生成未见过的配方**，以及与工作台隔离的 **反事实影子世界**。口径以 [`docs/影子世界与故障编译器计划.md`](影子世界与故障编译器计划.md) 和 [`docs/使用手册.md`](使用手册.md) 为准。

开发一个**用于模拟 IT 系统故障、由多个 AI Agent 协作分析原因、让人确认修复方案，再自动检测是否恢复**的 Web 平台。

不是普通聊天机器人：故障确实发生 → AI 根据真实日志诊断 → 产生处理建议 → 人工确认 → 执行预设修复 → 用真实探针验证结果。

### 先做3 种真实故障

| 场景 | 现场发生什么 | 系统应能做什么 |
|---|---|---|
| MySQL 故障 | 模拟数据库服务停止，业务查询失败 | 分析连接错误；经确认启动数据库；重新执行 SQL 检查 |
| Redis 故障 | 模拟缓存服务停止，业务缓存接口失败 | 分析缓存连接错误；经确认启动 Redis；重新测试读写 |
| Nginx 502 | 模拟后端应用停止，Nginx 返回 502 | 定位上游服务不可用；经确认恢复应用；重试 HTTP 接口 |

## 02. 整个系统先做 **5 个页面**

### 页面 1｜系统首页

**要显示：** 平台是否正常、是否连通、测试环境状态、3 类故障入口、最近的处理记录。

**用户能做：** 直接进入故障实验；点击历史记录查看处理结果。

### 页面 2｜故障实验中心

**要显示：** MySQL / Redis / Nginx 三张故障卡片；目标服务当前状态；故障前后的真实检测结果。

**用户能做：** 选择场景 → 点击注入故障 → 系统真的停止对应测试服务 → 查看异常 → 点击开始智能诊断；演示后可重置环境。

### 页面 3｜智能诊断工作台（整个项目的核心）

**要显示：** 当前工单状态、采集到的日志/探针、各 Agent 的执行步骤、AI 判断的故障根因、建议采取的修复动作、处理结果。

**4 个职责：** 证据采集 Agent（拿真实日志和状态）；故障诊断 Agent（HolmesGPT 分析根因）；处置规划 Agent（给出预设操作建议）；验证 Agent（用程序检查是否修复）。

**用户能做：** 看 Agent 流程和执行记录；阅读原因与证据；对修复动作点击同意或拒绝。拒绝后不执行；同意后由系统执行**白名单中的固定动作**。

### 页面 4｜故障记录与报告

**要显示：** 历史故障列表（时间、类型、状态、结果）；某次故障的证据、诊断、审批、执行与验证全过程。

**用户能做：** 筛选历史记录、打开详情、查看或导出简洁 Markdown 报告。

### 页面 5｜比赛评测页（后期完成）

**要显示：** 3 种故障的多轮测试记录、根因识别是否正确、是否修复成功、平均处理时间、失败案例。

**用户能做：** 查看测试结果与原始运行记录，不允许手填假结果。

## 03. 一次完整演示如何进行

以**Nginx 502**为例，完整流程如下：

1. 首页进入故障实验中心，选择 Nginx 502。
2. 点击注入故障，系统在 Docker 测试环境中停止 demo-app；代理接口真实返回 502。
3. 点击开始诊断，平台读取日志和探针，调用 HolmesGPT 分析故障原因。
4. 工作台显示各 Agent 的工作步骤，输出上游应用停止的根因和证据。
5. 规划 Agent 给出恢复 demo-app的建议；页面显示等待人工审批。
6. 用户点击同意修复，平台执行预先注册的启动动作，而不是执行 AI 任意生成的命令。
7. 验证 Agent 重新访问 Nginx 代理接口：返回 200 且响应正确 → **PASS**；否则 **FAIL / UNKNOWN**，记录原因，必要时再诊断一次。
8. 系统自动保存本次处理记录，展示处理报告。

**项目做成的标准：** 上述流程能在现场从头到尾运行，故障发生和恢复都能被实际检测证明，而不是只播放预设动画。

##  开发边界：这一个月明确不做

- 不接入真实公司生产服务器，不允许 AI 执行任意 Shell 命令。
- 不开发 Kubernetes 运维、不做复杂监控大屏和告警推送。
- 不做自由拖拽的 Agent 编辑器
- 不训练 AI 模型，不做手机 App、复杂权限和多租户。

**建议技术栈：** Vue3 + FastAPI + Python + HolmesGPT + LangGraph + Docker Compose + SQLite。
