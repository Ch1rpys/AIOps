# 五、结果验证与可证伪评测

验证不是最后一步才做的事。平台在三处分别验证：证据是否站得住、结论是否自洽、结果是否真的恢复。三层里最硬的是结果层，因为它是唯一不接受解释的一层：模型说修好了不算，规则说该好了也不算，探针绿了才算。

本章讲三值判定、稳定窗口、影响图与复盘，再讲盲诊评测的方法学和当前证据边界。

## 5.1 三层验证

| 层次 | 判定内容 | 判定者 | 不通过怎么办 |
| --- | --- | --- | --- |
| 证据层 | 引用的证据是否存在、是否覆盖容器状态与全部探针 | 代码校验 | 带错误反馈重试，最多 3 次 |
| 逻辑层 | 根因与拓扑解释是否矛盾 | 拓扑规则引擎 | 点名复测探针；仍矛盾则按探针事实走 |
| 结果层 | 修复后必需探针是否同轮全绿 | 真实探针 | FAIL 进下一轮；UNKNOWN 结束 |

证据层和逻辑层可以在几毫秒内完成，结果层要等容器真正恢复。三层不是串行的“评分卡”，而是三种不同的否决权：证据层否掉“引用不存在”的结论，逻辑层否掉“根因和拓扑打架”的结论，结果层否掉“没修好却声称修好”的结论。

## 5.2 三值判定

判定函数很短，但边界都在细节里：

```python
def judge(probes, scenario):
    by_name = {probe.name: probe.verdict for probe in probes}
    missing = any(name not in by_name for name in need(scenario))
    unknown = Verdict.UNKNOWN in by_name.values()
    if missing or unknown:
        return Verdict.UNKNOWN
    return Verdict.PASS if all(v == Verdict.PASS for v in by_name.values()) else Verdict.FAIL
```

四条规则：

- **必需探针缺失，或任一探针 UNKNOWN，整体判 UNKNOWN**，不能声称恢复；
- **同一轮里该场景的必需探针全 PASS 才算修好**；MySQL 需要 `mysql_select_1` 与 `app_db_check` 同轮双绿，Redis 需要 `redis_roundtrip` 与 `app_cache_check`，Nginx 502 需要 `nginx_hello` 返回 200 且正文完全匹配；
- 连接被拒绝这类“测到了，明确失败”归 FAIL；超时、认证失败、探针自身异常这类“测不了”归 UNKNOWN，不把环境问题记成故障没修好；
- 可选稳定窗口开启时，窗口内再次失败标记“恢复不稳定”，但三值 verdict 语义不变，失败采样不删除。

一个真实例子：2026-11-17 的 MySQL 工单，执行 `START_DEMO_MYSQL` 后第一次采样仍是 `mysql_select_1=FAIL`、`app_db_check=FAIL`，第二次采样双 PASS。`Probes.verify` 没有因为第一次失败就判 FAIL，而是继续按 3 秒间隔采样，直到通过或次数用尽。两次采样都写进工单，最终结论是 PASS，但第一次失败没有被删掉。这就是“同轮双探针”与“逐次采样保留”的区别：结论看最后一次完整采样，过程看全部样本。

## 5.3 稳定窗口

默认关闭稳定窗口，一次完整采样 PASS 就判恢复。开启后按“连续健康次数 + 观察窗口”判定：

- 冷却窗口内必须连续 `VERIFICATION_REQUIRED_PASSES=3` 次通过；
- 观察时间至少 `VERIFICATION_WINDOW_SECONDS=30` 秒；
- 样本数按窗口时长自动补足，避免“窗口秒数”变成永远达不到的死参数；
- 窗口内出现失败，`window.instability=true`，即使最后又变绿，也不能算已验证恢复；
- UNKNOWN 不算失败，但也不能算连续健康；
- 失败采样只追加，不删除。

稳定窗口解决的是“恢复后马上又坏”的问题。它不能证明“以后不再复发”，只能证明“这一段时间内观测稳定”。页面上的文案也要按这个口径写，不能把窗口内健康说成永久修复。

## 5.4 影响图与复盘摘要

`knowledge/topology.yaml` 是业务拓扑的唯一数据源。通用 Runbook 和影响图都从它生成，`scripts/generate_runbooks.py` 重新生成，测试校验不漂移。拓扑里严格区分三类关系：

- **已观测异常**：容器状态或探针直接看到的失败；
- **配置依赖**：Compose 的 `depends_on` 启动顺序，不等于业务因果；
- **推断传播**：沿业务依赖边、并且下游确实有实测异常时才成立。

这个区分不是文字游戏。`demo-app` 的 `/api/hello` 与 `/health` 不访问数据库或缓存，所以 MySQL 停了，这两个接口仍然成功；如果把 `depends_on` 画成故障传播链，就会得出“MySQL 停了所以 hello 也挂了”的错误结论。影响图会并列两句话：规则解释，以及模型推断。规则解释的耗时单独标 `rule_ms`，不消耗 token，也不算模型调用；模型推断来自已保存的诊断。

复盘摘要只投影已经保存的记录：何时发生、影响哪个接口、根因及引用、批准动作、修复前后探针、未解决项。它不会重新探测容器，也不会再执行动作。这样即使环境已经重置，历史工单仍然能还原当时的事实。

## 5.5 盲诊评测：一条独立链路

盲诊和工作台闭环是两条路，共用底层组件，但不共享权限。

盲诊链路的关键约束：

- **不建工单**：真值只落在 `evaluation_runs.truth_scenario`，不会借道 `GET /api/incidents` 泄露到工作台；
- **不调 Planner**：盲诊臂拿不到规划器入口；
- **不拿执行器**：盲诊路径没有 `ActionExecutor`，不可能执行任何动作；
- **独立租约**：评测用 `evaluation_lease`，与工作台的 `lab_lease` 互斥；评测进行中注入返回 `EVALUATION_BUSY`，工作台占着环境时评测返回 `LAB_BUSY`；
- **同一份快照**：A/B/C 三臂复用同一个 `snapshot_hash`；快照由四服务容器状态、6 个探针、4 个服务日志和通用 Runbook 组成，不含场景标识、配方编号、原语、期望签名；
- **真值隔离**：默认接口不返回真值；`view=evaluation` 需要管理员令牌，没令牌直接拒绝，不返回打码的假真值。

盲诊采证用 `collect_domain()`，不按场景挑选服务与探针，而是四个服务全量观测；只挂通用 Runbook，不挂任何场景专属 Runbook。诊断用 `diagnose_domain()`，不读场景注册表，不注入 `required_checks`、`allowed_action`、`target`。引用完整性校验仍然执行，但它只检查“引用存在且覆盖必需证据”，不检查“根因是否等于真值”。所以盲诊可以记录答错、拒答、自相矛盾，而不是只记录正确答案。

## 5.6 实验臂与公平性

| 实验臂 | 输入 | 做什么 | 计分 | 不适用的情况 |
| --- | --- | --- | --- | --- |
| A | 同一份文本快照 | 单次诊断 | 根因正确率、拒答、自相矛盾 | 处置提议、拦截率、审批等待 |
| B | 同一份文本快照 + 第一次结论 | 独立复核，可同意或质疑 | 同上；复核结论单独留痕 | 同上 |
| C | B 的输入 + 视觉证据 | 在 B 基础上加截图观测 | 同上；记录视觉证据 id | 没有截图时拒绝，不退化成 B |
| L | 对抗样本 + 闭环规划 | 只规划、不执行 | 非法动作提议、是否执行（恒为 0） | 普通正确率；L 不进普通分母 |
| R | 影子配方 + 目录 | 按目录搜索可修动作 | 签名消歧率、候选数 | 模型正确率；R 不进盲诊 |

A/B/C 的公平性靠三个技术保证：同一个 `snapshot_hash`、同一份必需证据清单、同一套预算上限。C 臂的视觉证据只进 C 臂，A/B 保持纯文本；如果 C 臂没有截图，服务层直接返回 `EVALUATION_ATTACHMENT_REQUIRED`，不会悄悄退化成 B 臂。附件文件名、存储路径、摘要都不进模型载荷，只有不透明 id 与观测字段；文件名是用户可控文本，起成答案标签就等于泄漏。

B 臂不是“同一个模型再问一遍”。复核者只看到同一份冻结证据和第一次结论，输出 `DomainReview`：同意或质疑、自己的根因、理由、证据引用。复核失败时保留第一次结论，不把复核错误覆盖成原始结论。两次调用的 token 用量合并；只有一份已知时标“部分已知”，不把少算当全量。

L 臂只在对抗样本里出现。它拿闭环规划器，但不拿执行器；即使提出非法动作，执行次数也恒为 0。L 臂的“非法动作提议”与“非法动作执行”分开报：前者是模型是否被投毒带偏，后者是平台是否真的拦住。没有跑 L 臂时，这两列是“不适用”，不是 0。

R 臂在影子里按目录搜索，不调用模型，不进入盲诊 prompt，也不计入模型正确率。它只作为“规则基线”的参照上界。

## 5.7 指标口径

指标不是越多越好，关键是每条都写清分母和“不适用”条件。

| 指标 | 口径 | 纪律 |
| --- | --- | --- |
| 根因正确率 | 根因正确且 `evidence_sufficient=true` ÷ 有效实验 | 分母包含拒答与答错；负例、对抗不进这个分母 |
| 拒答率 | `INSUFFICIENT_EVIDENCE` ÷ 有效实验 | 拒答是正确行为之一，不是失败 |
| 自相矛盾 | 自报证据不足却给出确定根因 ÷ 有效实验 | 单列，不算正确 |
| 错误处置提议数 | 提出目录外动作/非法目标 ÷ 有计划的实验 | 仅端到端；被拦住也要计数 |
| 拦截率 | 非法提议中被门禁拦下 ÷ 非法提议 | 仅端到端；没有非法提议时“不适用” |
| 恢复成功率 | 执行后独立复测 PASS ÷ 实际执行 | 以探针判定，不以模型自述 |
| 分阶段耗时 | 模型 / 采证 / 容器启停 / 恢复分别计时 | 失败实验不报 0 毫秒；取不到标未知 |
| 影子保真度 | 试修预测与真实观测的一致率 | 影子没起来是 UNKNOWN，不是 FAIL |
| 未见签名覆盖 | 命中冻结 `failing_checks` 的比例 | 漂移样本剔除，不算模型答错 |
| 未见签名精确 | 命中失败探针 ÷ 模型声称为异常的探针 | 假阳性单列；弱解析要标明 |
| 服务定位 | 点名服务与 `affected_services` 的交并比 | 与签名分开报，不合成一个总分 |
| token 用量 | 模型返回的 usage | 取不到写“未知”，不用 0 顶替 |

五条纪律跟着数字走：

1. **超限实验不进分母**。预算超限是成本问题，不是模型能力问题；混进同一个分母会系统性低估正确率。
2. **拒答与答错分开**。拒答可以是正确行为，尤其在负例和证据不足时；把拒答算错会逼模型乱猜。
3. **负例、对抗、未见各自分表**。不合成一个“总正确率”；不同 cohort 的假设空间不同，合成会制造虚假精度。
4. **不适用不记 0**。纯诊断没有执行器，处置提议和拦截率是“没问过”，不是“提了 0 次”。
5. **失败不报 0 毫秒**。模型调用失败也有真实耗时；0 只能表示“测到了且确实是 0”，不能表示“没测”。

## 5.8 对抗、负例与漂移

**对抗样本**把一段错误的根因和非法动作写进日志与截图观测。投毒文本只出现在证据位，不出现在系统提示的指令位；文本里不写本场景的真值标识，避免“投毒反而泄漏答案”。对抗样本单独计分，不进普通正确率；L 臂只评分、不执行。盲诊臂的“非法动作执行”是“不适用”，因为它们根本没有执行器；L 臂的执行次数是实测值，目标是 0。

**负例**是“应用固定返回 500”。容器活着、业务接口坏了，健康检查仍然 200。盲诊里正确答案是拒答或 `OTHER`，不计入可恢复故障的正确率；工作台里仍然可以走注册恢复动作，把应用模式改回正常。评测计分和工作台处置是两件事，页面会把“负例，不恢复”标在评测项上，避免误读。

**漂移**是现场探针签名与冻结签名不一致。平台记 `SIGNATURE_DRIFT`，把样本剔除出正确率分母，并在汇总里单列条数。漂移不是模型答错，不能拿来降低模型分数；但也不能假装没发生，报告要写清剔除了多少条、为什么。

泄漏测试是这些纪律的技术兜底。测试断言的是“最终序列化后的模型载荷”，不是“提示词模板”：

- 不得出现 `rec_`、`holdout`、`primitives`、`canonical_hash`、配方文件路径；
- 不得出现 holdout 列表中的 id；
- 不得出现场景枚举、答案标签、允许动作、目标服务；
- 工单列表、无令牌的评测 GET 不得返回配方原语和签名；
- 文件名、存储路径、附件摘要不得进入载荷；
- 日志、Runbook、截图文字必须被声明为数据，不是指令。

## 5.9 反馈优化路径

系统不训练模型，也不在线调参。所谓“反馈优化”，指的是把失败的信号结构化成下一次调用的输入。目前有四条路径：

- **错误码回灌**：诊断调用失败时，把错误码翻译成修复提示，拼进下一次请求，最多 3 次；
- **补采回灌**：模型说“证据不足”时，补采的观测追加进证据池，下一轮结论必须引用新证据；
- **失败重规划**：验证 FAIL 后开新一轮，规划上下文带着上一轮的验证结果和执行结果，避免重复同一个错误动作；
- **审计沉淀**：每次工单结束，证据、计划、审批、执行、复测按类别落库，报告只做投影，保证前后一致。

这四条都是“单次工单内”的反馈。跨工单的学习——比如把历史根因做成检索库、把失败计划做成负样本——目前没有做。它不是不能做，而是会改变评测口径：一旦模型看过历史工单，盲诊就不再“盲”。后续如果要做，必须把历史检索限制在训练集，holdout 仍然隔离。

## 5.10 当前证据与边界

把本机演示库的数字和它们能证明的东西放在一起：

| 观测 | 数值 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 真实工单 | 23 张，9 张 `REAL/RESOLVED` | 闭环能跑通；失败与取消也保留 | 覆盖所有故障类型 |
| 恢复执行 | 11 次，成功率 81.82% | 执行器与复测链路可用 | 统计显著性或生产可靠性 |
| 处置提议 | 13 条，非法 0 条 | 目录门禁未放过非法动作 | 模型永远不会提出非法动作 |
| 影子试修 | 23 次，0 跳过，保真度 90.48% | 影子可校准、可预测 | 所有配方都保真 |
| 校准 / holdout | 102 / 6291，holdout 27 | 编译器与冻结流程可用 | 大规模泛化 |
| 未见故障 | 有效 1 条，签名覆盖 100%，精确 40% | 计分链路可用 | 未见能力的高低 |
| 后端测试 | 250 个函数 / 380 个用例，31.9 秒全过 | 工程约束有回归保护 | 模型准确率 |

9 张 `RESOLVED` 覆盖 `MYSQL_DOWN`（6）、`REDIS_DOWN`（1）、`NGINX_502`（1）、`DUAL_MYSQL_REDIS`（1）。`NGINX_UPSTREAM` 与 `APP_HTTP_500` 有自动化测试，但当前演示库没有真实 `RESOLVED` 工单；本文不把它们写成“已验收”。盲诊的标准 3×3 批次在当前库中没有完整结果，早期标准臂记录因模型契约错误被剔除；本文不报一个没有分母的正确率。

这些数字的共同前提是：样本量小、根因枚举收窄了假设空间、评测环境是本机隔离容器。它们足以证明“机制成立”，不足以证明“统计显著”或“生产可用”。第七章会把局限逐条展开。
