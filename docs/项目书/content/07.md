# 七、测试、运行效果与工程评估

技术方案能不能站住，最后要看三件事：测试有没有守住边界、真实运行有没有留下证据、性能与局限有没有说清楚。本章按这三件事展开，数字全部来自当前仓库与本机演示库，不把测试夹具写成真实成绩。

## 7.1 测试策略

测试按“能真实就真实，不能真实才夹具”的原则分层：

- 编排、数据库、磁盘检查点用真实 LangGraph、SQLAlchemy 和 `SqliteSaver`；
- 只有 Docker、探针、模型三个外部边界用测试夹具；
- 所有测试工单强制标 `TEST/MOCK`，页面有横幅，不能当真实成绩；
- 浏览器交互测试使用独立入口 `backend/tests/ui_server.py`，数据库在 `data/test-ui`，不碰正式服务；
- 控制台回归使用 `backend/tests/console_server.py`，写请求全部路由到 TEST/MOCK 服务，真实环境只读。

当前后端有 27 个测试文件、250 个测试函数，`pytest` 参数化展开后是 380 个用例，31.88 秒全部通过。测试函数数与用例数不同，是因为 `parametrize` 会把一个函数展开成多条；报告里写“380 个用例”比写“250 个测试”更接近实际执行量。

CI 的顺序是：先跑 `check_holdout.py`，再跑 `pytest`。holdout 被改动，第一步就失败，不让“改完再跑”的侥幸过去。CI 目前只覆盖后端与 holdout；前端 lint/typecheck/build 和 Ruff 仍靠本地检查，这是 7.7 节列出的待补项。

## 7.3 关键测试举例

**幂等与并发。** `test_idempotency_injection_and_approval` 验证同键同请求返回第一次结果、同键异请求 409；`test_concurrent_injections_only_stop_once` 用并发请求验证容器只被停一次。注入和审批都可能被重复点击，幂等不是“优化”，是安全边界。

**中断恢复。** `test_checkpoint_survives_new_app_instance` 在一个新的 app 实例上恢复同一张工单，验证审批检查点真的落盘。`test_interrupted_run_visible_after_restart` 验证进程崩溃后的工单不会假装继续跑。

**执行不确定。** `test_uncertain_execution_never_replays` 模拟“动作可能已执行、回执没写入”，断言执行器抛 `EXECUTION_UNCERTAIN` 而不是再执行一次。这条测试直接对应 2.6 节的安全边界。

**模型不可用。** `test_model_outage_still_offers_registered_repair` 让诊断模型超时，断言只要探针证实故障，流程仍能生成注册恢复动作并停在审批；它不会伪造一条模型结论。

**泄漏。** `test_blind_payload_has_no_scenario_markers`、`test_attachment_filename_never_reaches_the_model_payload`、`test_unseen_summary_hides_recipe_ids` 断言的是最终序列化载荷，不是提示词模板。只检查模板会漏掉“模板里没有，但字段里带进去”的泄漏。

**评测公平性。** `test_arms_share_one_snapshot` 验证 A/B/C 的 `snapshot_hash` 相同；`test_only_c_arm_receives_the_visual_evidence` 验证视觉证据只进 C 臂；`test_c_arm_requires_a_visual_attachment` 验证 C 臂没有截图时明确拒绝，不退化成 B 臂。

**预算与失败保留。** `test_budget_exceeded_is_recorded_but_kept_out_of_the_denominator`、`test_failed_experiment_is_recorded_not_dropped`、`test_failed_run_does_not_report_zero_measurements` 三条一起守“失败不能消失、超限不能污染分母、失败不报 0 毫秒”。

**迁移。** `test_v1_database_upgrades_and_keeps_existing_rows`、`test_version_never_downgrades_on_reopen`、`test_unknown_version_is_rejected` 验证 schema 只升不降、旧库能迁、未知版本拒绝启动。

**影子。** `test_lock_busy_raises`、`test_compare_verdicts_raises_divergence`、`test_search_does_not_scan_all_then_variants`、`test_holdout_inject_is_forbidden` 分别守住世界锁、两界分歧、搜索空间裁剪和 holdout 隔离。

## 7.5 运行效果

先看一张完整的真实工单。2026-11-17 的 MySQL 故障工单 `inc_5be70a1896924a058b289eaab68aac1f`：

| 项目 | 实际值 |
| --- | --- |
| 场景 | `MYSQL_DOWN`，模式 `REAL` |
| 创建 → 结束 | 20:40:49 → 20:44:57，墙钟 248 秒 |
| 证据 | 12 条（容器状态、探针、日志、Runbook） |
| 诊断 | 1 次成功，根因 `MYSQL_SERVICE_STOPPED`，置信度 0.98，引用 5 条证据 |
| 规划 | 8.5 秒，动作 `START_DEMO_MYSQL`，目标 `demo-mysql`，命中目录 |
| 影子试修 | 18.65 秒；before 双 FAIL，after 六探针全 PASS；预测可完全恢复 |
| 批准 | 人工批准当前 `plan_id`；影子试修 18.65 秒、人工等待约 40 秒另计，审计里的 0 ms 是回执写入耗时 |
| 执行 | 227 毫秒，`START_DEMO_MYSQL` 成功 |
| 复测 | 2 次采样：第一次双 FAIL（启动抖动），第二次双 PASS；最终 `RESOLVED` |
| 证书 | 预测与实测 6/6 一致，匹配率 100% |

![真实工单的处置流程与耗时](assets/shots/workflow-timing.png)

图 7-1 同一张工单的七段耗时。采证 0.66 秒、诊断 172.6 秒、规划 8.5 秒、审批节点 0 毫秒、执行 227 毫秒、复测 3.1 秒；七段之和 185.1 秒。影子试修 18.65 秒与人工等待约 40 秒不在七段内，加上页面开销构成墙钟 248 秒。

这张工单说明了两件事。第一，耗时主要花在模型诊断，不是容器控制：诊断 172.6 秒，执行 0.227 秒；如果把“AI 很慢”归咎于 Docker，优化方向就错了。第二，复测第一次采样仍是 FAIL，平台没有因此判失败，而是继续采样到 PASS；如果只看第一次采样，就会把一个正在恢复的 MySQL 误判成“修不好”。

再看演示库的整体分布：

| 场景 | 工单数 | RESOLVED | 其他终态 |
| --- | --- | --- | --- |
| `MYSQL_DOWN` | 14 | 6 | 8 CANCELLED |
| `REDIS_DOWN` | 3 | 1 | 2 ERROR |
| `NGINX_502` | 1 | 1 | 0 |
| `DUAL_MYSQL_REDIS` | 2 | 1 | 1 CANCELLED |
| `COMPILED` | 3 | 0 | 1 CANCELLED、2 ERROR |
| 合计 | 23 | 9 | 14 |

`COMPILED` 的 3 张工单没有 RESOLVED；失败与取消被保留，没有为了报表好看而删掉。`APP_HTTP_500` 与 `NGINX_UPSTREAM` 在当前库中没有真实工单，只有自动化测试；本文不把它们写成“已验收”。

端到端指标：13 条处置提议、0 条非法提议、11 次执行、9 次恢复，恢复成功率 81.82%；模型调用 32 次，平均每张工单 1.39 次。影子侧 23 次试修、0 次跳过、保真度 90.48%、部分恢复预测 73.53%、R 臂签名消歧率 33.3%、平均试 4 个候选。未见故障只有 1 条有效计分，签名覆盖 100%、精确 40%；样本量太小，不能当成能力结论。

## 7.6 性能与资源

**单次闭环的耗时结构。** 以上面的 MySQL 工单为例，墙钟 248 秒，其中模型诊断 172.6 秒、规划 8.5 秒、复测 3.1 秒、采证 0.66 秒、执行 0.23 秒；七段之和 185.1 秒。影子试修 18.65 秒发生在审批节点内部，人工从影子试修完成到点击批准约 40 秒，加上页面轮询与记录开销，构成 248 秒墙钟。模型调用是绝对瓶颈；容器启停和探针验证都在秒级。这个结构决定了优化优先级：先做模型超时、重试和预算，再做容器并发。

审批等待目前没有单独入库：审计里的审批节点只记录回执写入的 0 毫秒，人工阅读与点击约 40 秒只能从影子试修完成时间、审批回执时间和工单结束时间推算。这是指标层的一个缺口，后续应把“等待人工”作为独立阶段记录，避免把人的思考时间混进模型耗时。

**资源。** 9 个容器（真环境 5 个含 Holmes，影子 4 个），本机建议 16GB 内存；所有端口只绑回环；SQLite WAL + 进程文件锁；后端单 worker。当前没有做压测，不报 QPS、P95 或并发用户数；这些数字在单 worker、单实验的架构下没有意义。

**预算。** 模型单次 90 秒；评测单次 15 秒 × 3 次 = 45 秒；未见评测单次 180 秒、总 300 秒；Docker 20/30 秒；探针 3 秒；补采 45 秒；复测 5 次 × 3 秒。预算是上限，不是必须花满的配额；A 臂天然只调 1 次，用不完额度，这本身就是结果的一部分。

**可扩展性边界。** 单 worker 是硬限制，第二实例会被 `data/platform.lock` 拒绝；SQLite 在多租户前必须换 PostgreSQL；9 个容器已经接近一台 16GB 笔记本的舒适上限。项目当前的目标是“一台机器跑通一次真实闭环”，不是“支撑生产流量”；等目标变了，这些边界要重新设计，而不是在原架构上打补丁。

## 7.7 局限与下一步

| 局限 | 当前表现 | 下一步 |
| --- | --- | --- |
| 并发与存储 | 单 worker、SQLite，只能单实验 | 迁移 PostgreSQL；引入任务队列；按工单隔离租约 |
| 样本量 | 23 张工单、9 张 RESOLVED；标准 3×3 盲诊批次未完整跑 | 跑 3×3 基线，扩到百条量级，补置信区间 |
| 场景覆盖 | 四容器拓扑；`APP_HTTP_500`、`NGINX_UPSTREAM` 无真实 RESOLVED 工单 | 补真实闭环；增加网络分区、磁盘、依赖超时等原语 |
| 评测 | 未见故障有效 1 条；根因枚举收窄假设空间 | 扩 holdout 与校准池；报告显式声明枚举限制 |
| 学习能力 | 不训练、不检索历史、不自动调参 | 历史根因检索（训练集隔离）；离线评测后再上线 |
| 工程门禁 | Ruff 62 条告警；CI 未跑前端与 Ruff | 清理风格告警；CI 增加前端 lint/typecheck/build 与 Ruff |
| 平台验收 | macOS ARM64 本机已跑通；Windows 未本轮复验 | Windows 双击脚本复验；补充 ARM64 镜像报告 |
| 成本核算 | token 取不到时写“未知”，未做费用估算 | 接入 usage 与计价版本；按工单出成本报表 |

这些局限里，最需要优先解决的是“样本量”和“真实场景覆盖”。平台的方法学已经就位，但 9 张成功工单不足以证明统计显著性；评委如果问“正确率是多少”，诚实的回答是“标准批次还没跑完，不能给一个可信的数字”。这比报一个漂亮的假数字更符合项目的“可证伪”立场。

## 7.8 结论

本平台做的事情可以概括成一句话：**把 AI 运维从“给建议”推进到“可批准、可执行、可复测、可证伪”的闭环。**

技术上，它用故障编译器把六个场景扩展成 6291 条可执行配方，用影子世界在批准前做反事实试修，用 3046 条动作目录把模型输出关进固定条目，用 LangGraph 的中断审批把人的决定写进检查点，用独立探针和只追加审计保证结果不靠模型自述，用 A/B/C/L/R 对照和 holdout 把“准不准”变成可复核的实验。

工程上，它坚持单机可复现、执行权集中、失败保留、指标口径写死；27 个测试文件、380 个用例覆盖了幂等、并发、重启恢复、执行不确定、泄漏、预算、迁移、影子分歧等真实失败模式；真实工单留下了诊断、计划、审批、执行、复测和证书，失败与取消也没有被删掉。

它还不是一个生产系统：单 worker、SQLite、样本量小、场景有限、部分场景没有真实闭环。但这些边界是写出来的，不是藏起来的。下一阶段要做的，是把 3×3 基线和更多真实场景跑完，把检索式学习限制在训练集内，把并发与存储换成可扩展的方案；在那之前，平台至少已经证明了一件事：**模型的判断可以被组织成一条有边界、有证据、有判决的工程链路，而不是一段无法复核的聊天记录。**
