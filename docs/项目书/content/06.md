# 六、核心实现、数据与界面

本章从代码和数据角度说明平台是怎么落地的：后端怎么分包、动作目录怎么把模型输出收进固定条目、探针怎么区分 FAIL 与 UNKNOWN、审计记录长什么样、前端 8 个视图各自负责什么。最后放几张真实运行截图，截图里的工单、探针和耗时都来自本机演示库。

## 6.2 动作目录与执行器

动作目录当前 3046 条，按类别分布如下：

| 类别 | 条数 | 说明 |
| --- | --- | --- |
| `then` 链式动作 | 2610 | 动作 + 复测探针的组合，例如“启动 MySQL 后复测 `mysql_select_1`” |
| `nginx_timeout` | 294 | 连接/读/发三组超时网格 |
| `life` | 31 | 四个服务的启动、停止、重启、重建、暂停、恢复、杀死 |
| `cpu_limit` / `mem_limit` | 32 | 0.1/0.2/0.5 CPU、32m/64m/128m 内存 |
| `netem_delay` / `netem_loss` / `netem_clear` | 32 | 延迟、丢包、清除 qdisc |
| `mysql` | 12 | 12 条登记 SQL |
| `net` | 8 | 四个服务的 connect / disconnect |
| `redis` | 7 | PING、DBSIZE、INFO、GET/SET/DEL health、FLUSHDB |
| `app_mode` | 4 | 500、slow、empty、wrong_json |
| `nginx_profile` | 3 | healthy、misdirected、mysql、blackhole 中的可执行项 |
| `mysql_max_connections` / `redis_maxmemory` / `redis_maxmemory_policy` | 10 | 连接数与内存策略网格 |
| `none` / 密码类 | 3 | `NO_ACTION`、改乱实验密码、重置密码 |

目录不是“动作 ID 的数组”。每条条目都带目标、类型、参数、摘要和固定操作；`perform(docker, action_id)` 只接受目录里的编号，按条目类型调用控制器。模型输出里的空格、引号、分号、冒号、斜杠、`1s`、`1/2/2`、`docker compose up -d demo-mysql`、`mysql -e SELECT 1`、带容器序号的名字，会先被归一化再对到目录；否定句（`can't restart`、`不应该重启`）不会被当成要执行；`apply restart` 这种误伤也不会。计划里多出来的 `shell` 字段会被丢掉，不会拿去执行。

执行器只做三件事，但每件都不能省：

```python
validate_plan(plan, scenario)          # 目录、目标、登记探针
approved = any(
    a.payload["plan_id"] == plan_id and a.payload["decision"] == "approve"
    for a in approvals
)
if not approved:
    raise DomainError("BLOCKED", "没有该计划的有效人工批准")
if item.detail["plan_id"] != plan_id or item.status != Status.EXECUTING:
    raise DomainError("BLOCKED", "计划已过期或状态不允许执行")
```

执行记录分三段写：`STARTED`、`SUCCEEDED` / `FAILED` / `UNKNOWN`。如果同一 `plan_id` 已经有成功记录，直接返回上次结果，不再动容器；如果已有 `STARTED` 但没有结论，抛 `EXECUTION_UNCERTAIN`，要求人工检查后重置。这个设计承认“Docker 写操作和本地事务不能原子提交”的现实，不假装可以自动重试。

## 6.3 探针、证据与脱敏

六个探针是平台与现场之间的唯一“事实接口”。每个探针都返回三值 verdict 和原始观测，不是只返回一个布尔值。

| 检查 ID | 怎么测 | PASS 条件 | FAIL / UNKNOWN 边界 |
| --- | --- | --- | --- |
| `mysql_select_1` | pymysql 连隔离库执行 `SELECT 1` | 返回 `(1,)` | 连接拒绝 FAIL；认证/库不存在（1044/1045/1049）UNKNOWN |
| `app_db_check` | `GET /db-check` | 200 且正文 `{"status":"ok","value":1}` | HTTP 非 200 或正文不符 FAIL；网络异常 UNKNOWN |
| `redis_roundtrip` | PING + SET/GET `aiops:health` | PING 成功且读回 `probe` | 连接拒绝 FAIL；认证/超时 UNKNOWN |
| `app_cache_check` | `GET /cache-check` | 200 且正文 `{"status":"ok","value":"probe"}` | 同上 |
| `nginx_hello` | `GET http://127.0.0.1:18080/api/hello` | 200 且正文完全匹配 `{"message":"hello from demo-app"}` | 502/500 FAIL；连接异常 UNKNOWN |
| `app_health` | `GET /health` | 200 且正文 `{"status":"ok"}` | 用于排除“整个应用死了”，不是某场景的唯一判据 |

采证时，`EvidenceAgent` 把容器状态、该场景的探针、相关服务日志、场景 Runbook、可选截图统一成 `Evidence` 对象。每条证据有 `id`、`source`、`kind`、`raw`、`captured_at`；附件还有可选的 `attachment` 元信息。日志入库前做两层脱敏：把 `.env` 里的数据库密码、Holmes key、Planner key、管理员令牌替换成 `[REDACTED]`；再用正则把 `password=...`、`api_key=...`、`authorization=...` 这类模式替换掉。

盲诊采证用另一条路径 `collect_domain()`：四个服务全量观测、六个基线探针、四个服务日志、通用 Runbook；不按场景挑选，不挂场景专属 Runbook，不传 `scenario_key`、`required_checks`、`allowed_action`、`target`。这条路径与闭环采证并列，而不是替换闭环；两条路径共用证据模型和引用完整性判据。

## 6.4 故障编译器的实现

编译器目录有 10 个文件，各管一件事：

| 文件 | 职责 |
| --- | --- |
| `schema.py` | 配方、原语、签名的 Pydantic 模型；16 类原语的参数网格校验 |
| `hash.py` | 规范 JSON、SHA-256、`rec_` 编号 |
| `enumerate.py` | 单/双/白名单三、四原语枚举与约束过滤 |
| `primitives.py` | 原语 → 控制器调用；逆操作；静态先验 |
| `calibrate.py` | 影子注入、采证、签名、拆除、回基线 |
| `split.py` | seen / holdout 冻结、生成清单、CI 校验 |
| `canonical.py` | 六个规范场景作为编译器的特例 |
| `apply.py` | 对某个 World 注入/拆除配方 |
| `score.py` | 未见故障签名计分 |
| `titles.py` | 只描述可观测症状的人类可读标题 |

`apply_recipe` 和 `undo_recipe` 很薄，但它们保证了“只有一条注入路径”：

```python
def apply_recipe(docker, recipe):
    outputs = [apply_primitive(docker, item, undo=False)
               for item in recipe.primitives]
    return outputs[0] if len(outputs) == 1 else {
        "operation": "recipe", "recipe_id": recipe.id, "outputs": outputs
    }

def undo_recipe(docker, recipe):
    outputs = [apply_primitive(docker, item, undo=True)
               for item in reversed(recipe.primitives)]
    return outputs[0] if len(outputs) == 1 else {
        "operation": "recipe_undo", "recipe_id": recipe.id, "outputs": outputs
    }
```

注意 `undo_recipe` 按相反顺序执行。多条原语的拆除顺序错了，可能出现“先把网络接回来，再停容器”这种无意义操作；逆序是最小但必要的正确性条件。

## 6.5 影子世界与证书

`TwinService` 管三件事：世界锁、试修、证书。

- **世界锁**：`data/twin.lock`，`FileLock(timeout=0)`；抢不到抛 `TWIN_BUSY`，不排队等待。影子试修是独占资源，排队会让页面看起来“卡住”。
- **试修**：先 `reset_to(recipe)`，再 `perform(action_id)`，采 before/after，再 reset 回配方态；任何一步失败都记 `skipped` 与原因，不编预测。
- **证书**：真环境复测后，拿 `trial.after` 与实测探针逐项比较，算 `match_rate`，记录 `surprise`（预测有值、实测有值但不一致的探针）。

```python
def certificate(self, trial, observed_probes):
    predicted = trial.get("after") or {}
    observed = {p.name: p.verdict.value for p in observed_probes}
    match = {n: predicted.get(n) == observed.get(n) for n in CHECK_IDS}
    matched = sum(1 for n in CHECK_IDS if match[n])
    return {
        "predicted": predicted,
        "observed": observed,
        "match": match,
        "match_rate": round(matched / len(CHECK_IDS), 4),
        "surprise": [n for n in CHECK_IDS
                     if predicted.get(n) != observed.get(n)
                     and predicted.get(n) and observed.get(n)],
        "trial_id": trial.get("id"),
    }
```

当前演示库 23 次试修、0 次跳过，平均保真度 90.48%。这个数字的分母是 6 个探针 × 每张证书，样本仍然很小；它能说明“影子不是摆设”，不能说明“所有配方都保真”。

## 6.6 盲诊评测的实现

`EvaluationService` 的核心是三个隔离：

- **数据隔离**：不建工单，真值只在 `evaluation_runs.truth_scenario`；实验臂记录在 `evaluation_runs` / `evaluation_arms`。
- **权限隔离**：不调 Planner、不拿执行器；盲诊路径没有执行入口。
- **环境隔离**：`evaluation_lease` 与 `lab_lease` 互斥；评测结束无论成功失败都拆除故障、恢复基线。

预算对象是每个实验臂一份，覆盖该臂自己的模型调用和额外补采；两臂共用的采证与容器启停单独计时，不摊到臂上。`Budget.check()` 在每次调用前查次数和耗时，超限抛 `EVALUATION_BUDGET_EXCEEDED`，记录为超限样本，不混进正确率分母。

一次实验的步骤是：取基线 → 注入 → 采证直到故障成立 → 冻结快照（哈希）→ 逐臂跑 → 拆除并恢复基线 → 落库。任何一步失败，都要给每个请求的臂留一条失败记录；失败样本不能凭空消失。

## 6.7 审计记录长什么样

审计表是平台最重要的“黑匣子”。本机演示库当前有 677 条审计记录，类型分布如下：

| 类型 | 条数 | 用途 |
| --- | --- | --- |
| `evidence` | 321 | 容器状态、探针、日志、Runbook、附件 |
| `step` | 106 | 节点运行轨迹、耗时、输入摘要、输出 |
| `reset` | 58 | 环境重置的回执 |
| `twin_trial` | 35 | 影子试修的前后探针、跳过原因 |
| `probe_sample` | 27 | 复测逐次采样 |
| `execution` | 24 | 动作执行开始/成功/失败/未知 |
| `injection` | 20 | 故障注入回执 |
| `run` | 17 | 一次工作流运行 |
| `plan` / `plan_proposal` | 16 / 13 | 被接受计划 / 所有提议（含被拦） |
| `approval` | 13 | 人工批准/拒绝 |
| `verification` | 12 | 一轮复测结论 |
| `twin_certificate` | 7 | 预测/实测证书 |
| `twin_search` / `recipe_inject` / `calibration` | 3 / 3 / 2 | R 臂搜索、配方注入、校准 |

`plan_proposal` 与 `plan` 分开，是为了统计“非法提议”和“被拦住”的比例：提议先落 `plan_proposal`，过门禁后才落 `plan`。如果只记录被接受的计划，非法提议就永远不会出现在分母里。

## 6.8 前端 8 个视图

前端不是“把 API 结果画出来”，而是把“当前处于哪个阶段、下一步能做什么”讲清楚。导航 8 个入口，对应 8 个视图文件；下表把“基线探针”标签页与独立的修复对比卡也列出来，便于对照路由：

| 视图 | 路由 | 作用 | 刷新 |
| --- | --- | --- | --- |
| 故障实验 | `/lab` | 六场景卡片、编译器随机注入、确认弹窗、基线门禁 | 15 秒 |
| 环境管理 | `/environment` | 四容器、影子容器、平台自检、租约、重置 | 15 秒 |
| 基线探针 | `/environment?tab=probes` | 6 个探针的原始返回 | 15 秒 |
| 故障编译器 | `/compiler` | 池子摘要、配方列表、holdout 折叠、按配方注入 | 手动 |
| 影子世界 | `/twin` | 影子容器、探针、日志、最近试修 | 15 秒 |
| 故障记录 | `/incidents` | 场景/状态筛选、分页、报告下载 | 手动 |
| 智能诊断工作台 | `/incidents/:id` | 流程、根因、证据、影响图、审批、复测、复盘 | 2 秒 |
| 盲诊评测 | `/evaluation` | 触发实验、各臂对照、e2e、对抗、负例、未见、保真 | 8 秒 |
| 修复对比卡 | `/incidents/:id/card` | 故障时/恢复后对比、影子预测、AI 做了什么、导出 PNG | 手动 |

页面不产生判定结果。PASS/FAIL/UNKNOWN 全部来自服务端；前端只做展示和交互。管理员令牌只保存在页面内存，刷新后要重新粘贴；普通只读接口不带令牌，只有写操作和评测视图带。这样既减少了凭据暴露面，也让“只读浏览”不需要配置。
