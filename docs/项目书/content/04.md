# 四、多智能体编排与受限调度

“多智能体”很容易被理解成几个模型互相聊天。本平台的定义更窄：多智能体是把不同的判断源放到不同的权限位，让模型可以错，但错误必须被另一个角色抓住。诊断模型、规划模型、复核模型、验证探针各司其职；拓扑规则、影子试修和真实探针不依赖模型，负责“否”。

本章讲工作流怎么走、每一步由谁决定、失败后怎么循环，以及为什么这些循环不会失控。

## 4.1 角色与判断源

系统里有 4 个模型相关角色和 3 个非模型判断源。

| 角色 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- |
| 证据采集 | 容器状态、6 个探针、4 个服务日志、Runbook、可选截图 | 带 id 与采集时间的 Evidence 列表 | 只读；日志入库前脱敏 |
| 故障诊断 | 证据快照 + 通用 Runbook | 根因、摘要、证据引用、置信度、候选与补采请求 | 必须引用真实证据 id；不得执行动作 |
| 处置规划 | 诊断结论 + 动作目录 | 动作编号、目标、理由、期望探针 | 只能引用目录条目；目标由目录对齐 |
| 独立复核（B 臂） | 同一份冻结证据 + 第一次结论 | 同意/质疑、自己的根因、证据引用 | 只用于评测；不进入执行链 |
| 拓扑规则 | `topology.yaml` + 实测探针 | 应有症状、冲突判定、三类关系 | 不调模型；毫秒级 |
| 影子试修 | 配方 + 计划动作 | 预测差分、是否可修 | 只在影子执行；不碰真环境 |
| 真实探针 | 6 个注册检查 | PASS / FAIL / UNKNOWN | 缺失或未知一律 UNKNOWN |

这张表里最重要的是“独立复核”和“真实探针”两行。前者让 B 臂不是“同一个模型再问一遍”，而是拿同一份证据做一次有约束的复核；后者让“修没修好”不依赖任何模型的自我陈述。

## 4.2 九节点状态机

工作流用 LangGraph 的 `StateGraph` 实现，状态是 `TypedDict`，节点是绑定方法，条件边是纯函数。九个节点是：采集、重采、诊断、补采、执行许可、规划、审批、执行、复测。七处条件分支分别决定“继续、重来、补采、改走注册动作、等人、结束”。图 4-1 画出主路径的七步；重采与补采两个辅助节点在转移表中展开。

![九节点工作流](assets/fig-4-1-workflow.png)

图 4-1 工作流主路径（七步）。补采是诊断子图里的唯一回边；采证重试与复测新一轮是另外两处循环。

完整的转移关系如下。读的时候注意两点：`supplement` 是诊断子图里唯一的“回边”，它把流程送回 `diagnose`；`verify` 的 FAIL 不是原地重试，而是 `collect_retry` 开新一轮，新一轮必须重新审批。

| 当前节点 | 条件 | 下一节点 | 说明 |
| --- | --- | --- | --- |
| `collect` | 观测完整，或该场景故障已被探针证实 | `diagnose` | 不在采证处死等 |
| `collect` | 证据不完整且重采次数 < 2 | `collect_retry` | 只重采一次 |
| `collect` | 重采后仍不完整 | `END` | 判 UNKNOWN，记 `EVIDENCE_INSUFFICIENT` |
| `diagnose` | 结论通过引用完整性校验 | `authorize` | 校验失败带反馈重试，最多 3 次 |
| `diagnose` | 模型不可用或结论不可用，但探针已证实故障 | `authorize` | 改走注册诊断，标注来源 |
| `diagnose` | 模型请求补采，且轮次/预算未用尽 | `supplement` | 只补注册检查 |
| `diagnose` | 截图与实测冲突且未补查 | `collect` | 先补采一轮再判 |
| `supplement` | 补采完成 | `diagnose` | 新证据必须被下一轮结论引用 |
| `authorize` | 模型根因与拓扑解释矛盾，且未复测 | `supplement` | 复测规则点名的探针 |
| `authorize` | 结论通过执行许可，或故障成立但结论不足 | `plan` | 后者改走注册恢复动作 |
| `plan` | 计划命中目录、目标与探针一致 | `approval` | 连续 2 次非法则 BLOCKED |
| `approval` | 人工批准且 `plan_id` 一致 | `execute` | 拒绝则 CANCELLED |
| `execute` | 执行成功 | `verify` | Docker 失败则 ERROR |
| `verify` | 同轮必需探针全 PASS | `END` | RESOLVED |
| `verify` | FAIL 且 attempt < 2 | `collect_retry` | 开新一轮，重新审批 |
| `verify` | FAIL 且 attempt = 2 | `END` | FAILED |
| `verify` | UNKNOWN | `END` | 不猜，直接结束 |

“执行许可”是一个容易被忽略的节点。它不调模型，只做两件事：把模型根因和拓扑解释对账；在矛盾时点名叫哪条探针复测。它的耗时单独记 `rule_ms`，不计入模型调用次数。这样做是为了避免把“规则引擎的毫秒级对账”算成“模型又思考了一次”。

## 4.3 节点守卫与审计

每个节点外面都套了一层 `guarded` 包装器。它负责计时、写审计、接异常、把错误码映射成工单终态。节点内部抛出的 `DomainError` 不会把整个图打崩，而是变成工单的 `error` 字段和终态。

```python
def guarded(self, state, phase, operation, label=None):
    started_at, start = now(), time.monotonic()
    self.phase(state, phase)
    try:
        result = operation()
        outcome = "SUCCEEDED"
    except DomainError as failure:
        terminal = {
            "BLOCKED": Status.BLOCKED,
            "EVIDENCE_INSUFFICIENT": Status.UNKNOWN,
            "EVIDENCE_CONFLICT": Status.UNKNOWN,
            "PROBE_UNAVAILABLE": Status.UNKNOWN,
        }.get(failure.code, Status.ERROR)
        result = {"error": {"code": failure.code, "message": failure.message}}
        self.phase(state, terminal, **result)
        outcome = "FAILED"
    record = {
        "run_id": state["run_id"],
        "attempt": state["attempt"],
        "phase": phase,
        "step_kind": label or phase,
        "status": outcome,
        "started_at": started_at,
        "ended_at": now(),
        "elapsed_ms": round((time.monotonic() - start) * 1000),
        "output": result,
        "input_digest": {"evidence_ids": [e["id"] for e in state.get("evidence", [])]},
    }
    self.store.audit(state["incident_id"], "step", record)
    return result
```

这里有一个实现细节：`phase` 和 `step_kind` 分开。诊断阶段里既有真正调用 Holmes 的步骤，也有几毫秒的执行许可检查；前端的六个阶段按 `phase` 渲染，统计模型调用次数时只认 `step_kind`。如果不分开，“执行许可”会被算成一次模型调用，成本数字就不真实。

审计记录只追加，不更新。每条记录带 `run_id`、`attempt`、`started_at`、`ended_at`、`elapsed_ms`、`output`、`input_digest`。工单详情、报告、复盘摘要都从这些记录投影，不重新执行容器动作。这样即使模型或 Docker 后来变了，历史工单仍然能按当时的事实回放。

## 4.4 interrupt 审批与恢复

审批节点用 LangGraph 的 `interrupt`，不是前端弹窗。中断点会把状态写进 `checkpoints.sqlite3`，进程重启后从审批节点继续。恢复时代码先校验审批携带的 `plan_id` 与当前计划是否一致，不一致直接判 `BLOCKED`。

```python
response = interrupt({
    "plan_id": state["plan_id"],
    "plan": state["plan"],
    "attempt": state["attempt"],
    "twin_trial": trial,
})
if response.get("plan_id") != state["plan_id"]:
    raise DomainError("BLOCKED", "审批对应计划不匹配")
```

这里有一个容易踩的坑：`interrupt` 恢复时，节点会从头执行一遍。如果节点在中断点之前有副作用，恢复时就会重放。平台的解决办法是：影子试修在 `interrupt` 之前完成并落库；恢复时先查这一轮有没有试修记录，有就直接复用，不再重跑。测试 `test_checkpoint_survives_new_app_instance` 用一个新的 app 实例恢复同一张工单，专门守这个语义。

审批拒绝不执行任何动作，工单变 `CANCELLED`，故障保留，实验租约也保留。要再注入，必须先重置环境。审批通过则进入执行；执行器再次校验目录、目标、探针、人工批准和 `plan_id`，四道核验缺一不可。

## 4.5 证据契约与三层门禁

诊断契约是一个严格的 Pydantic 模型：`root_cause` 只能取六个值，`summary` 1–4000 字，`evidence_ids` 至少一条，`confidence` 0–1，`evidence_sufficient` 是严格布尔值；`candidates`、`requested_checks`、`affected_services`、`failing_check_ids` 是可选扩展字段。

校验分两层，顺序不能反：

```python
def validate_diagnosis(diagnosis, evidence, scenario):
    validate_evidence_integrity(diagnosis, evidence)      # 引用存在 + 覆盖必需证据
    validate_execution_preconditions(diagnosis, evidence, scenario)  # 允许执行
```

**引用完整性**只看证据本身：引用的 id 必须真实存在，且必须覆盖容器状态与全部探针证据。它不查场景，因此盲诊也能用它——答错和拒答都要能落库，不能因为“结论不对”就把记录拦掉。

**执行许可**才查场景：`evidence_sufficient` 必须为真，根因必须命中该场景的注册值，实测故障必须成立；负例场景（应用固定 500）不允许进入审批。只有闭环入口调用它，盲诊路径永远不调用。

这个拆分是评测方法学的基础。如果只有一层“必须答对才放行”，盲诊就只能记录“正确答案”，错误样本全部消失，正确率无从统计；如果只有“引用存在”一层，闭环又可能放行一个根因不对的计划。两层分开，闭环严、盲诊宽，才既能安全执行，又能测量能力。

模型输出不合契约时，平台不会立刻失败。诊断最多 3 次，规划最多 2 次；每次重试把错误码翻译成修复提示，拼进下一次上下文；模型的原始输出保存在 `raw_model_output` 里。`json_object` 模式下，模型有时会把唯一的诊断对象包进数组，平台会展开“恰好一个对象”的数组再校验；两个或更多对象仍然拒绝。校验失败不是“模型能力不足”的自动结论，只有重试耗尽且探针也没证实故障时，才收尾为 `AI_INVALID_RESPONSE`。

## 4.6 补采与拓扑复核

补采是系统里最像“主动感知”的一步：模型看完第一轮证据，可以申请再看几个检查。但它只能从 6 个注册检查里点，而且每次都要说明理由。

- 请求结构是 `check_id + reason`，最多 3 条，服务端按轮次预算截断；
- 已经采过的检查不重复采；
- 最多 2 轮，每轮最多 2 项，总耗时 45 秒封顶；
- 补采完回到诊断节点重来一轮，新证据必须被下一轮结论引用，否则引用完整性不通过；
- 轮次、项数、总耗时任一触顶就停止，并把“为什么停”写进工单，不静默截断。

拓扑复核走同一条补采通道，但触发条件不同：模型根因和 `topology.yaml` 的解释矛盾时，规则引擎点名要复测的探针，补采一次后再判。补采后仍矛盾，只要探针已经证实故障，就改走注册恢复动作；探针没证实故障，才以 `EVIDENCE_CONFLICT` 收尾。这避免了“模型和规则吵架，流程卡死”的常见问题。

## 4.7 预算与刹车

预算不是事后统计，是事前约束。所有循环都有上限，而且这些上限在启动时会被自检一遍。

| 环节 | 上限 | 超限后的行为 |
| --- | --- | --- |
| 诊断 | 3 次尝试 | 退到注册诊断，标注结论来源 |
| 规划 | 2 次尝试 | 判 BLOCKED，不进入审批 |
| 补采 | 2 轮、单轮 2 项、总 45 秒 | 停止补采，记录原因后继续 |
| 复测 | 5 次采样、间隔 3 秒、最多 2 轮 | 保持 FAIL，进入下一轮或结束 |
| 模型单次调用 | 90 秒 | 按失败处理，计入重试 |
| 评测单臂 | 3 次调用、总 45 秒、单次 15 秒 | 超限实验单列，不进正确率分母 |
| 未见评测单臂 | 3 次调用、总 300 秒、单次 180 秒 | 同上；未见诊断没有场景提示，单独预算 |
| Docker 调用 | 20 秒（影子 30 秒） | `DOCKER_UNAVAILABLE` |
| 探针 | 3 秒 | 该探针 UNKNOWN，不伪造 FAIL |
| 评测租约 | 900 秒 | 过期清理；进程崩溃不会永久锁死工作台 |

评测预算有一条硬约束：`EVALUATION_MODEL_TIMEOUT × EVALUATION_MAX_MODEL_CALLS` 必须不大于 `EVALUATION_BUDGET_SECONDS`（默认 15×3=45）。这条约束在 `Settings` 的 `model_validator` 里检查，不满足直接拒绝启动。原因是 `httpx` 不能在途中断请求，预算检查只能发生在两次调用之间；如果单次调用可能突破总预算，“超限终止”就永远落不到实处。

## 4.8 自我循环

系统里有四个不同时间尺度的循环，它们共用同一套证据和审计，但触发条件和终止条件不同。

| 循环 | 触发 | 一圈做什么 | 终止条件 |
| --- | --- | --- | --- |
| 单工单循环 | 复测 FAIL | 重新诊断、重新规划、重新审批、再执行 | 两轮用尽，或 UNKNOWN |
| 校准循环 | 编译器生成新配方 | 影子注入、采证、拆除、回验基线 | 签名稳定，或校准失败 |
| 评测循环 | 触发盲诊实验 | 同一快照跑 A/B/C/L；R 臂在影子侧跑，记录指标 | 预算耗尽或实验完成 |
| 数据循环 | 每次工单结束 | 审计落库，沉淀根因—证据—动作—验证记录 | 持续；跨工单学习尚未实现 |

单工单循环最容易被误读：它不是“失败就重试”，而是“失败后开新的一轮，带新的计划、重新审批”。第一轮的批准不会被复用，第二轮的动作如果和第一轮相同，执行器会直接返回上次结果，不再动容器。这样既避免了重复副作用，也避免了“用旧批准执行新计划”的越权。

四个循环各有刹车，合起来保证系统不会无限转：

- **轮次刹车**：诊断 3 次、规划 2 次、补采 2 轮、验证 2 轮，任一处用尽就收尾；
- **预算刹车**：单次超时与总预算双重约束，超限单列而非重跑；
- **语义刹车**：UNKNOWN 直接结束，不猜；拒绝审批不执行；计划不命中目录不进审批；
- **物理刹车**：同一时刻只允许一个实验占环境，评测与工作台互斥，执行不确定禁止自动重放。

## 4.9 模型不可用时的注册修复

演示现场最常见的意外不是“模型答错”，而是“模型超时、密钥过期、网关限流”。如果这时流程直接停在半路，故障会一直留在环境里。平台的处理是：只要探针已经证实该场景的故障，就改走该场景注册的恢复动作，并在工单上注明“模型没有给出可用结论，已按探针和注册动作继续，批准后才会执行”。

这条路径有三个限制：

1. 只有探针证实故障才触发；探针没证实，不编造修复；
2. 注册动作仍然要人工批准，不是自动执行；
3. 来源标成 `registered_repair`，不把规则补救说成模型的原话。

如果模型只提出 `NO_ACTION`，而探针仍显示故障，平台会留下这条提议，然后改用该场景的优先动作。`NO_ACTION` 不能用来结束一个已经被探针证实的故障；这是“模型可以选择不做事，但不能用不做事掩盖故障”的边界。
