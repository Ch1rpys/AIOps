# 二、总体架构与技术选型

架构的价值不在于组件列表，而在于它能否把第 1.3 节的四种权力变成可检查的边界。本平台的做法是：先把依赖方向固定成“只向下”，再把所有外部副作用收进唯一一层，最后用文件锁、租约、幂等键和只追加审计把并发与重试的边界钉死。

## 2.1 设计原则

**单机可复现。** 评委或客户拿到仓库，双击一个脚本就能在本机把真环境、影子世界、Holmes 和前端拉起来。放弃 Kubernetes 和云原生编排，换来的是“一台笔记本能跑完一次闭环”。代价是容量和并发上限，所以当前只支持单 worker、单实验。

**执行权集中。** 只有集成适配层可以产生外部副作用；领域服务层只能调用目录动作；接口层不直接碰 Docker；模型层连 Docker Socket 都看不到。依赖方向一旦反过来，审计就会出现盲区。

**模型无状态。** 模型不持有会话记忆，不直接读写数据库，不直接操作容器。每次诊断只拿到平台给它的证据快照；每次规划只拿到诊断结论和动作目录。模型的状态全部落在工单与检查点里，进程重启后可以恢复。

**事实与解释分离。** 容器状态、探针结果、日志是事实；根因、影响传播、恢复预测是解释。事实由采集器写入，解释由模型或规则生成；两者在页面上分栏展示，在数据里分开存储。解释可以被推翻，事实不可以被覆盖。

**失败保留。** 失败工单、超限实验、拒答、漂移样本都不删除。报告只做投影，不重新执行容器动作，也不把失败样本从分母里悄悄拿掉。

**只向下依赖。** 表现层依赖接口层，接口层依赖编排层，编排层依赖领域服务，领域服务依赖集成适配，最后落到存储。反向依赖通过事件、审计记录或查询接口解决，不允许下层直接回调上层。

## 2.2 运行时拓扑

一次完整演示在本机拉起 9 个容器、2 个进程和 2 个 SQLite 文件。所有端口只绑 `127.0.0.1`，不连外网也能完成一次闭环（模型调用除外）。

| 组件 | 地址 / 端口 | 作用 | 关键约束 |
| --- | --- | --- | --- |
| 控制台 | `http://127.0.0.1:5173` | 8 个视图，轮询真实 API | 页面不产生判定结果 |
| 平台 API | `http://127.0.0.1:8000` | 39 个 REST 路由 | 单 worker；`data/platform.lock` 拒绝第二实例 |
| HolmesGPT | `http://127.0.0.1:5050` | 诊断推理，只读证据 | 版本钉死 0.45.0；全部工具关闭；不挂 Docker Socket |
| 真环境 MySQL | `127.0.0.1:13306` | 隔离数据库 | 仅 `aiops-demo` 项目；独立数据卷 |
| 真环境 Redis | `127.0.0.1:16379` | 隔离缓存 | 独立数据卷 |
| 真环境应用 | `http://127.0.0.1:18000` | 业务接口与健康检查 | 固定模式文件控制 200/500/slow |
| 真环境 Nginx | `http://127.0.0.1:18080` | 反向代理入口 | 活动配置由平台写入并重载 |
| 影子 MySQL / Redis | `23306` / `26379` | 影子世界数据层 | 独立项目、端口、卷 |
| 影子应用 / Nginx | `28000` / `28080` | 影子世界业务层 | 独立 Nginx 与应用模式文件 |

真环境与影子世界不是“同一个 Compose 项目换个名字”。它们有独立的 Compose 文件、独立的项目名、独立的端口、独立的卷、独立的 Nginx 活动配置和独立的应用模式文件。`World` 抽象把项目名、网络名、端口、配置路径收进一个不可变对象，`DockerController` 和 `Probes` 只对某个 `World` 说话。这样做的目的不是多起四个容器，而是保证“在影子里试修”不会通过共享文件或共享网络打到真环境。

## 2.3 六层职责

| 层级 | 关键组件 | 职责 | 硬边界 |
| --- | --- | --- | --- |
| 表现层 | Vue 3.5、Element Plus 2.14、Vite 7.3、TypeScript 5.9 | 8 个视图；工单详情 2 秒轮询、评测 8 秒、环境 15 秒 | 不计算 PASS/FAIL；不保存判定；不直接调用 Docker |
| 接口层 | FastAPI 0.162、Pydantic 2.14 | 39 个路由（25 GET / 14 POST）；统一错误体；令牌、Origin、幂等 | 写操作必须管理员令牌；注入/重置/审批/评测必须幂等键 |
| 编排层 | LangGraph 1.2、SqliteSaver 3.1 | 9 节点状态机；`interrupt` 审批；检查点恢复 | 节点只通过结构化状态传递；异常映射成工单终态 |
| 领域服务层 | 实验控制、证据、目录、执行器、验证、编译器、影子、评测（自研） | 事务、互斥、受限执行、审计、计分 | 不能直接拼 Shell；不能绕过目录与审批 |
| 集成适配层 | Docker CLI、HolmesGPT、独立 Planner、视觉模型、6 个探针 | 唯一允许产生外部副作用的一层 | 参数数组、固定 context、超时、错误码、脱敏 |
| 存储层 | SQLAlchemy 2.0、SQLite | 10 张业务表、检查点、附件 | schema v4 只升不降；WAL；进程级文件锁 |

“39 个路由”不是把接口拆得越细越好，而是把只读查询、写操作和评测视图分开。只读接口不需要令牌，写接口统一经过 `require_admin`，评测真值只有带令牌的 `view=evaluation` 才返回。接口层的职责是校验形状和权限，不替领域层做业务判断。

## 2.4 技术选型

选型原则只有一句：**能用成熟组件的不自己写，凡是涉及执行权的地方一律自己写。**

| 选型项 | 采用方案 | 主要备选 | 理由与代价 |
| --- | --- | --- | --- |
| 编排 | LangGraph 1.2 + SqliteSaver | 自研状态机、Airflow | 原生 `interrupt` 与检查点，审批可以真的中断并跨重启恢复；代价是要吃透“恢复时节点从头执行”的语义 |
| 诊断 | HolmesGPT 0.45.0（Apache-2.0） | 直接调通用大模型 | 已封装 SRE 调查流程；平台关闭全部工具，只把它当“读证据给结论”的推理层；镜像 tag 与 digest 钉死 |
| 规划 | 独立 OpenAI 兼容端点 | 与诊断共用同一模型 | 诊断与规划分开调用，避免同一模型自证；换提供商只改配置 |
| 服务端 | FastAPI 0.162 + Pydantic 2.14 | Flask、Django | 契约校验强、异步友好、自带 OpenAPI 文档；代价是 Pydantic 版本升级要跟 |
| 前端 | Vue 3.5 + Element Plus + Vite 7 | React、原生模板 | 组件齐、上手快；刷新用轮询不引 WebSocket，少一层状态 |
| 存储 | SQLite + SQLAlchemy 2.0 | PostgreSQL、MySQL | 单机零依赖、事务够用；代价是只能单 worker，多租户前必须迁移 |
| 容器控制 | Docker CLI + 固定 `default` context | Docker SDK、Shell 脚本 | 参数数组调用、主动剥离 `DOCKER_HOST` 等变量，每次调用可审计；不传 Shell |
| 依赖管理 | uv + npm lock | pip + requirements | 锁到具体版本，任何一台机器装出来都一样，便于复现 |

当前本机实际版本为：Python 3.11.18、FastAPI 0.162.0、Pydantic 2.14.2、SQLAlchemy 2.0.55、LangGraph 1.2.19、`langgraph-checkpoint-sqlite` 3.1.3、Vue 3.5.44、Element Plus 2.14.7、Vite 7.3.7、TypeScript 5.9.3、MySQL 8.4.7、HolmesGPT 0.45.0。Holmes 镜像为 `holmes:0.45.0@sha256:a6edc272...`，版本与摘要同时锁定，避免“latest 一升级，行为就变”。

## 2.5 数据模型与状态机

工单有 14 个状态。它们不是装饰性的枚举，而是把“谁在等谁”写进了状态机：`WAITING_APPROVAL` 是正常停点，不是故障；`UNKNOWN` 是“观测不足”，不是失败；`BLOCKED` 是“越权被拦”，不是流程异常。

| 分组 | 状态 | 页面文字 | 含义 |
| --- | --- | --- | --- |
| 准备 | `CREATED` | 准备注入 | 工单已建，故障尚未确认 |
| 准备 | `INJECTED` | 故障已确认 | 探针已证实故障，可以开始诊断 |
| 运行 | `COLLECTING` | 采集证据 | 容器、探针、日志采集中 |
| 运行 | `DIAGNOSING` | HolmesGPT 诊断 | 含模型调用与执行许可 |
| 运行 | `PLANNING` | 制定计划 | 独立规划模型 |
| 等待 | `WAITING_APPROVAL` | 等待人工审批 | 正常停点；批准前真环境零副作用 |
| 运行 | `EXECUTING` | 处理审批 / 执行动作 | 已批准，正在执行目录动作 |
| 运行 | `VERIFYING` | 独立复测 | 逐轮采样，同轮必需探针全 PASS 才恢复 |
| 终态 | `RESOLVED` | 已验证恢复 | 释放实验租约 |
| 终态 | `CANCELLED` | 已取消 | 人工拒绝；故障仍在 |
| 终态 | `FAILED` | 恢复失败 | 两轮复测仍未通过 |
| 终态 | `UNKNOWN` | 结果未知 | 观测未知，或补查后仍看不到故障 |
| 终态 | `ERROR` | 流程异常 | 节点异常或 Docker 失败；旧工单不自动续跑 |
| 终态 | `BLOCKED` | 动作被拦截 | 计划不匹配、审批不匹配、工具未关闭 |

业务库共 10 张表。核心设计是“工单主表 + 只追加审计 + 幂等回执 + 两把租约 + 评测/配方/影子表”。审计表不更新、不删除；报告层只读它做投影，不重新执行任何容器动作。

| 表 | 存什么 | 关键约束 |
| --- | --- | --- |
| `incidents` | 工单主表：场景、模式、状态、详情 JSON | 状态 14 个；终态不可回退 |
| `audit_records` | 证据、步骤、计划、执行、复测、审批、影子试修、校准 | 只追加；按 rowid 回放 |
| `request_receipts` | 幂等键与请求指纹 | 同键同请求复用响应；同键异请求 409 |
| `lab_lease` | 工作台实验占用的单行租约 | 同一时刻只允许一个实验；成功恢复后释放 |
| `evaluation_lease` | 盲诊评测占用的单行租约 | 与工作台互斥；TTL 900 秒，过期清理 |
| `evaluation_runs` | 每次实验臂的记录 | 真值只在 `truth_scenario`；默认接口不返回 |
| `evaluation_arms` | 实验臂配置快照 | 记录模型、prompt 版本、超时 |
| `recipes` | 编译配方与签名 | 规范哈希唯一；holdout 标记 |
| `twin_trials` | 影子试修记录 | 含跳过原因、耗时、前后探针 |
| `twin_certificates` | 预测/实测证书 | 匹配率；预测失败单独记录 |

Schema 当前为 `user_version=4`，支持从 0、1、2、3 升级；版本号只升不降，读到未知版本直接拒绝启动。迁移分支是显式的：旧库不再走 `create_all`，增量内容由迁移负责。这样做牺牲了一点开发便利，换来的是“不会因为换了一个二进制，历史库被悄悄改坏”。

## 2.6 安全边界

安全不是一句“只绑回环”。平台把威胁拆成具体的控制点，每个控制点都能在代码里指出来。

| 威胁 | 控制 | 落点 |
| --- | --- | --- |
| 未授权写操作 | `X-Admin-Token` + `hmac.compare_digest`；只对写路由生效 | `api/routes.py:require_admin` |
| 跨站写请求 | `Origin` 白名单；`TrustedHostMiddleware` 只允许本机 host | `app/main.py` |
| 模型生成任意命令 | 目录编号；`shell=False`；参数数组；服务白名单；固定 context | `services/action_catalog.py`、`integrations/docker.py` |
| Holmes 自行调工具 | 版本核验 + 工具集必须全关；发现工具即 `BLOCKED` | `integrations/models.py:check_capabilities` |
| 双实例并发 | `data/platform.lock` 文件锁；单 worker | `app/main.py:lifespan` |
| 重复请求 / 重放 | 幂等键 + 请求指纹；同键异请求 409 | `repositories/store.py` |
| 密钥进入日志或证据 | `SecretStr` 注入；日志与证据统一 `redact` | `agents/evidence.py:redact` |
| 真环境与影子串味 | `World` 抽象；独立项目、端口、卷、配置路径 | `app/worlds.py` |
| 执行结果不确定 | `EXECUTION_UNCERTAIN`；禁止自动重放 | `services/executor.py` |
| 数据库版本漂移 | `user_version` 白名单；未知版本拒绝启动 | `repositories/store.py` |

其中两条值得单独说明。

**第一条是“审批不是弹窗”。** 审批记录里必须同时有当前 `plan_id`、`decision`、操作者、幂等键；执行器再次校验工单状态和 `detail.plan_id`。上一轮的批准不能用于下一轮，伪造的 `plan_id` 会在 `INVALID_STATE` 或 `BLOCKED` 处被拦下。

**第二条是“执行不确定时不重放”。** Docker 的写操作和本地事务无法原子提交：命令可能已经生效，但回执还没写入。遇到这种情况，执行器记 `EXECUTION_UNCERTAIN`，让工单停住，要求人工检查环境后重置；它不会“再试一次”，因为再试一次可能把已经启动的服务重启一遍，或者把一个正在恢复的数据库再打断。

## 2.7 关键取舍

| 取舍 | 选择 | 换来了什么 | 付出了什么 |
| --- | --- | --- | --- |
| 单机 vs 云原生 | 两个 Compose 工程、单机 SQLite | 评委一台笔记本能跑；部署链路短 | 并发上限低；多租户前要换存储 |
| 目录 vs 工具调用 | 3046 条自研动作目录 | 执行可审计、可回滚、可测试 | 每加一类动作都要写代码、进目录 |
| 影子双跑 vs 演示速度 | 独立 `aiops-twin`，4 个同镜像容器 | 批准前有反事实预测；校准有场地 | 资源翻倍；多一把世界锁；试修耗时 |
| SQLite vs PostgreSQL | 单文件 + WAL + 文件锁 | 零依赖、易打包、事务够用 | 只能单 worker；复杂查询能力有限 |
| 轮询 vs WebSocket | 2s / 8s / 15s HTTP 轮询 | 前端状态简单；断线恢复容易 | 实时性一般；请求数略多 |
| 不训练 vs 微调 | 只做提示、契约、目录和评测 | 可复现；不依赖 GPU；模型可替换 | 领域适配靠工程约束，不靠权重 |

这些取舍没有“绝对正确”，只有“和当前目标匹配”。本项目的目标是竞赛 MVP：让评委在有限时间里看到一条真实闭环，并且能自己复现；不是做一个多租户 SaaS。等目标变了，存储、并发和前端实时性都要重新选。
