# 一、问题定义与需求边界

AIOps 的讨论很容易停在“能不能定位根因”。但在真实运维现场，定位只是中间产物：更昂贵的问题是“定位之后敢不敢动”“动完算不算真的好”“换一道没见过的题还灵不灵”。本平台把这三个问题合并成同一件事——把一次故障处置做成可执行、可审计、可证伪的实验。

本章先说明问题从哪里来、现有做法缺什么，再给出七条硬需求和明确的场景边界。后续六章分别回答：架构怎么落、故障空间怎么造、智能体怎么编排、结果怎么判、系统怎么实现、质量怎么证明。

## 1.1 三个断层

**第一个断层：发现与诊断之间。** 监控系统擅长回答“哪里不对”：指标越线、探针变红、告警收敛。它不回答“为什么不对”。大模型可以读日志、读状态、读 Runbook，但如果没有证据约束，它很容易把“看起来像”说成“就是”。一句没有证据 id 的根因，事后无法复核，也无法判断是模型推理还是猜中。

**第二个断层：诊断与处置之间。** 让模型直接生成 Shell 命令，等于把生产环境交给一个不可复现的采样过程；把处置写死成脚本，又只能覆盖预先想到的路径。很多“AI 运维”演示停在“模型给出了建议”，因为再往前一步就要面对权限、回滚、幂等和审计。人工审批如果只是点一下“同意”，既没有计划级绑定，也没有执行前的副作用隔离，那么审批只是形式。

**第三个断层：处置与验证之间。** “容器起来了”“命令返回 0”“模型说修好了”都不是恢复。恢复必须由独立于模型的观测来判定，而且要在同一轮里覆盖该场景的全部必需探针。更严格一点：一次成功不能证明系统可靠，还要看失败样本是否保留、没见过的故障是否还能定位、对抗输入会不会被带偏。

| 断层 | 常见做法 | 留下的缺口 | 本平台的应对 |
| --- | --- | --- | --- |
| 发现 → 诊断 | 告警 + 大模型总结 | 结论无证据引用，错答与拒答混在一起 | 诊断契约强制引用容器状态与全部必需探针；证据 id 不存在即拒绝 |
| 诊断 → 处置 | 模型生成命令 / 固定脚本 | 越权、不可回滚、审批与计划脱钩 | 3046 条动作目录；模型只报编号；审批绑定当前 plan_id；执行前四道核验 |
| 处置 → 验证 | 看容器状态 / 看命令回执 | 把“启动了”当成“恢复了” | 独立探针同轮双 PASS；FAIL 开新一轮并重新审批；UNKNOWN 明确收尾 |
| 单次演示 → 能力证明 | 挑一个场景演一遍 | 场景泄漏、无对照、失败被删 | 盲诊独立链路、A/B/C 对照、同快照指纹、holdout、对抗样本、失败样本保留 |

## 1.2 为什么“演示一次成功”不能证明系统可用

一个看起来很顺的演示，可能同时藏着五类“假成功”：

- **场景泄漏。** 模型上下文里出现场景名、允许的动作、该看哪几个探针，模型不需要诊断，只需要对号入座。
- **答案泄漏。** 工单标题、Runbook 文件名、截图文件名里带着根因标签，模型读到的其实是答案。
- **执行越权。** 模型给出的命令被直接执行，恰好这次没出事，但没有任何机制保证下一次不出事。
- **判定自证。** 执行成功就记恢复，没有独立探针；或者只跑一个探针，另一个仍然红着。
- **失败消失。** 演示失败就删掉工单重跑，直到出现一张全绿截图；分母里只剩下成功样本。

本平台的设计几乎都是在逐条堵这五类漏洞。盲诊链路不把场景标识、动作目录、期望探针写进模型上下文；评测真值只落在 `evaluation_runs.truth_scenario`，默认接口不返回；执行器永远拿不到模型生成的命令；复测由独立探针完成；失败工单保留，报告只做投影、不重算。

## 1.3 命题：把处置变成可证伪的实验

“可证伪”在这里不是哲学修辞，而是五条可检查的工程性质：

1. **故障真实发生。** 容器真的停、代理真的 502、数据库连接真的被拒绝；不是回放一段预录日志。
2. **证据可引用。** 每条证据有 id、来源、采集时间；诊断引用的 id 必须真实存在，且覆盖容器状态与全部必需探针。
3. **动作受限且可执行。** 模型只能从登记目录里选编号；编号在代码里编译成固定操作；没有 Shell、任意 SQL、任意路径。
4. **结果独立判定。** PASS / FAIL / UNKNOWN 由探针给出；同一轮必需探针全绿才算恢复；观测未知时明确说“不知道”。
5. **过程可复现、可评测。** 同一份证据快照可以跑多个实验臂；同一份配方在另一台机器上得到同一个哈希；同一批 holdout 不被改动。

这五条性质对应四种权力：模型保留**判断权**，程序保留**执行权**，人保留**批准权**，探针保留**判决权**。四权分立，任何一权越界，闭环就不再可证伪。

![四权分立|14](assets/fig-1-1-four-rights.png)

图 1-1 处置链上的四权分立。模型只出判断，程序只执行登记动作，人保留批准权，探针保留最终判决权。

## 1.4 七条硬需求

把上面的命题拆成可验收的需求，得到七条。它们不是并列的功能清单，而是互相拉扯的约束：R3 要求收紧权限，R4 要求放开验证；R2 要求证据充分，R7 要求环境轻量。后面的架构取舍，基本都在这几对矛盾里做选择。

| 编号 | 需求 | 对应机制 | 主要落点 |
| --- | --- | --- | --- |
| R1 | 故障必须真实发生 | Docker 控制器按参数数组停容器、改 Nginx 配置、改应用模式、断网；注入后 3 次确认 | `backend/app/integrations/docker.py`、`services/faults.py` |
| R2 | 证据必须来自现场 | 容器状态快照 + 6 个注册探针 + 4 个服务日志 + Runbook + 可选截图，统一成 Evidence | `agents/evidence.py`、`integrations/probes.py` |
| R3 | AI 不能直接动环境 | 3046 条动作目录；模型只报编号；执行器校验目录、目标、探针与人工批准 | `services/action_catalog.py`、`services/executor.py` |
| R4 | 结果必须实测 | 同轮必需探针全 PASS 才判恢复；缺失或 UNKNOWN 判 UNKNOWN | `integrations/probes.py:judge` |
| R5 | 全过程可追溯 | 审计记录只追加；按 rowid 回放；报告只投影已保存记录 | `repositories/store.py`、`services/review.py` |
| R6 | 能力可评测 | 盲诊独立链路、A/B/C/L/R 对照、同快照指纹、holdout、对抗样本 | `services/evaluation.py`、`services/compiler/` |
| R7 | 部署要轻 | 单机两个 Compose 工程、9 个容器、2 个 SQLite 文件、所有端口只绑回环 | `deploy/*.yml`、`scripts/` |

七条需求里，R3 和 R4 是“安全”的两端：R3 让模型不能动手，R4 让模型不能自证。R2 和 R6 是“可信”的两端：R2 保证证据是真的，R6 保证能力不是靠一次演示吹出来的。R1 是前提，R5 是底线，R7 是让评委和客户能自己跑一遍的交付条件。

## 1.5 场景与边界

平台限定在一个隔离的四容器拓扑：MySQL、Redis、应用、Nginx，外加一套端口、卷、配置目录都独立的影子世界。场景不大，但它覆盖了数据库、缓存、应用、网关四类最常见的故障点，也足够把闭环上的每个环节逼出来。

在场景层面，平台提供两层能力：

- **六个规范场景**：MySQL 停止、Redis 停止、Nginx 502（应用停止）、Nginx 上游配置错误、应用固定 500、MySQL 与 Redis 同时停止。它们是编译器也能生成的特例，工作台保留按钮入口。
- **故障编译器生成的配方**：16 类登记原语，1–4 条组合，枚举去重后 6291 条；其中 102 条经过影子校准，27 条冻结为 holdout。工作台可以从 seen 池随机注入，评测只从 holdout 抽题。

![六类规范场景](assets/shots/lab-scenarios.png)

图 1-2 六类规范场景。每张卡片都写明目标容器与恢复判据；确认框展示实际目标，不展示模型不知道的答案。


| 做 | 不做 |
| --- | --- |
| 本机 Docker 隔离环境中的真实故障注入与恢复 | 接入公司生产服务器或真实业务系统 |
| 四容器拓扑上的诊断、规划、审批、执行、复测 | Kubernetes 运维、复杂监控大屏、告警推送 |
| 目录内的固定动作与固定参数 | 让模型执行任意 Shell、任意 SQL、任意路径 |
| 单机、单 worker、单实验的竞赛 MVP | 多租户、分布式调度、高并发 |
| 盲诊评测与可复现基线 | 训练模型、在线学习、自动调参 |
| 显式拓扑、影响图与复盘摘要 | 自由拖拽的 Agent 编辑器 |

边界写在这里，是为了避免两种常见误读：一种是把“平台能修四种容器”读成“平台能修任何生产故障”；另一种是把“模型能给出根因”读成“模型可以自己动手”。本平台既不扩权，也不假装覆盖边界之外的东西。

## 1.6 四个技术贡献

**贡献一：把故障从枚举变成语言。** 六个场景只是六条单原语配方。平台用配方 DSL、组合约束、规范哈希和影子校准，把故障空间扩展到 6291 条可执行、可拆除、可计分的配方，并用 27 条冻结 holdout 回答“没见过的题还能不能做”。

**贡献二：批准之前先做反事实。** 影子世界使用独立 Compose 项目、独立端口、独立卷和独立配置目录，在人工批准之前把计划动作试跑一遍，输出逐探针的预测差分；真环境复测后再生成预测/实测证书。预测失败不被改写成成功，影子起不来就明确记“跳过”。

**贡献三：把执行权关进目录。** 3046 条动作目录把“服务 × 动词”“登记 SQL × 结果”“动作 + 复测探针”编译成不可变条目；模型只能报编号，执行器在执行前校验目录、目标、探针、人工批准和当前 `plan_id`。审批用 LangGraph `interrupt` 真正中断，不是前端弹窗。

**贡献四：把“模型准不准”变成可复核的实验。** 盲诊链路不建工单、不调 Planner、不拿执行器入口；A/B/C 三臂复用同一份文本快照的 `snapshot_hash`；C 臂只多一份视觉证据；L 臂只在对抗样本里出现且不执行；R 臂在影子里做目录搜索，作为非模型基线。指标口径写死，“不适用”不记 0，超限实验剔除分母，token 取不到就写未知。

截至本文写作时的本机演示库，真实闭环累计 23 张工单、13 条处置提议、11 次执行、9 张 `REAL/RESOLVED` 工单，恢复成功率 81.82%；影子试修 23 次、0 次跳过、保真度 90.48%；校准池 102 条、holdout 27 条；后端 27 个测试文件、250 个测试函数，`pytest` 展开 380 个用例全部通过。这些数字的样本量都不大，本文会在第七章逐条说明它们能证明什么、不能证明什么。
