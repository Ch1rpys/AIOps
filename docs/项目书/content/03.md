# 三、故障空间工程：编译器、校准与影子世界

六个场景可以证明“闭环能跑”，但证明不了“模型会诊断”。因为六个场景的注入方式是六个分支，模型只要记住“MySQL 停了就选 START_DEMO_MYSQL”，就能在演示里全对。要回答泛化问题，必须先把故障从“枚举”变成“语言”，再给这门语言一套可执行、可校准、可冻结的语义。

本章讲三件事：配方怎么定义、真值怎么校准、批准前怎么在另一个世界里试一遍。

## 3.1 从枚举到语言

原来的注入逻辑是 `scenarios.py` 里的六个分支：停 MySQL、停 Redis、停应用、改 Nginx 上游、改应用模式、同时停两个。每条分支对应一个固定的 `action` 和一个固定的根因标签。这个结构适合做 MVP，但不适合做评测：场景名一旦进入模型上下文，正确率就变成了“对号入座率”。

故障编译器把这六个分支拆成更小的原语，再用组合规则重新生成故障。它有三个输出：

- **可执行**：一组注入步骤和拆除步骤，对真环境和影子都能执行；
- **可计分**：一份校准后的探针签名，说明哪些检查失败、哪些仍然通过、波及哪些服务；
- **可识别**：一个由内容决定的规范哈希，同一组原语在另一台机器上得到同一个 `rec_` 编号。

编译器不是一个“随机故障按钮”。它是一个纯函数加一次可选校准：纯函数负责枚举、约束、哈希；校准负责把“我觉得会红”变成“影子实测确实红”。前者保证可复现，后者保证真值不是手写的。


## 3.2 配方 DSL 与 16 类原语

一条配方由 1–4 条原语组成。原语只允许 16 类，每一类的参数都来自固定网格或固定文件，不接受模型或用户传入的自由字符串。

| 原语 | 参数 | 注入效果 | 拆除 | 先验失败探针 |
| --- | --- | --- | --- | --- |
| `life` | service + stop / pause / kill / recreate | 停止、暂停、杀死或重建容器 | start / unpause | 该服务对应探针 |
| `net` | service + disconnect / connect | 断开或接回演示网络 | connect | 依赖该服务的业务探针 |
| `nginx_upstream` | healthy / misdirected / mysql / blackhole | 切换固定的 Nginx 配置 | healthy | `nginx_hello` |
| `nginx_timeout` | connect/read/send 超时网格 | 写固定超时配置并重载 | healthy | `nginx_hello` |
| `app_mode` | ok / http_500 / slow / empty / wrong_json | 写固定应用模式文件 | ok | `nginx_hello`（500 时 `app_health` 仍 PASS） |
| `mysql_statement` | 12 条登记语句 | 在隔离库执行登记 SQL | 无副作用或对应逆操作 | 视语句 |
| `mysql_password` | scramble / reset | 改成仓库内第二份已知乱码 / 改回实验密码 | reset | `mysql_select_1`、`app_db_check` |
| `redis_op` | 7 个登记操作 | 对隔离 Redis 执行登记操作 | 视操作 | 视操作 |
| `poison_logs` | 无 | 只污染采证，不改容器 | 清除工单投毒标记 | 无；签名不变，标负例 |
| `cpu_limit` | 0.1 / 0.2 / 0.5 | `docker update --cpus` | 恢复默认 | 该服务对应探针 |
| `mem_limit` | 32m / 64m / 128m | `docker update --memory` | 取消限制 | 该服务对应探针 |
| `netem_delay` | 50 / 100 / 200 / 500 ms | 容器内 `tc qdisc` 延迟 | 删除 qdisc | 依赖该服务的业务探针 |
| `netem_loss` | 5 / 10 / 20 % | 容器内 `tc qdisc` 丢包 | 删除 qdisc | 依赖该服务的业务探针 |
| `mysql_max_connections` | 2 / 5 / 10 | `SET GLOBAL max_connections` | 改回镜像默认 | `mysql_select_1`、`app_db_check` |
| `redis_maxmemory` | 1mb / 4mb / 16mb | `CONFIG SET maxmemory` | 0（无限制） | `redis_roundtrip`、`app_cache_check` |
| `redis_maxmemory_policy` | noeviction / allkeys-lru | `CONFIG SET maxmemory-policy` | 改回默认 | `redis_roundtrip`、`app_cache_check` |

原语表里有三类东西值得单独说明。

**第一类是“容器还活着，但业务坏了”。** `app_mode=http_500`、`nginx_upstream=misdirected`、`mysql_password=scramble` 都不会停容器。它们逼着模型去看“容器状态全 running，但某个业务探针失败”的证据组合，而不是简单地把“谁 exited”当成唯一线索。应用固定 500 的场景里 `/health` 仍然是 200，这是故意的：容器活着、业务接口坏了，不能靠“把应用启动一次”来修。

**第二类是“参数只能来自网格”。** CPU、内存、延迟、丢包、连接数、Redis 内存上限都只允许固定取值。模型不能写 `--cpus=0.37`，也不能写 `tc qdisc add ... 123ms`。这不是为了限制表现力，而是为了让“校准过的签名”和“可拆除的逆操作”成立：如果参数是连续的，拆除和复现都不可靠。

**第三类是“不可逆也要显式登记”。** `mysql_password=scramble` 的逆操作是 `reset_demo_password`，用的是仓库内第二份已知乱码和 `.env` 里的实验密码；模型不能提供密码字符串。`poison_logs` 只改采证内容，不改容器，所以它单独出现时标 `negative=true`，不进未见故障的正确率分母。

配方本身是一个严格模型：`primitives` 1–4 条，`schema_version=1`，`id` 由内容哈希派生，`title` 只描述可观测症状，不写根因枚举名。`recoverable`、`negative`、`poison`、`canonical_scene`、`preferred_actions` 都是配方的元数据，不参与哈希。标题可以改，编号不会变；这是“同一道题不能靠改名字变成另一道题”的技术保证。

## 3.3 枚举、约束与规范哈希

枚举器先列全部合法单原语，再列双原语组合；三、四原语只保留白名单模式，避免组合爆炸产生大量没有意义的题。每条组合都要过约束过滤器：

- 不得四个服务全部停止；
- 同一服务不得同时 `stop` 与 `pause`，也不得出现两个生命周期动词；
- `nginx_upstream` 与 `nginx_timeout` 互斥，活动配置只有一份；
- `app_mode`、`poison_logs` 每条配方至多一条；
- 负例（只改不影响探针的东西）单独标记，不进未见分母；
- 拆除不在目录里的原语标 `recoverable=false`，工作台不得编造修复。

去重后得到 6291 条配方。数量本身不是目的，目的是让“没见过的组合”有足够大的采样空间，同时每一条都能注入、能拆除、能校准。

规范哈希的实现很短，但它是整个编译器可复现性的根：

```python
def canonical_hash(primitives):
    payload = [
        item.model_dump(mode="json", exclude_none=True)
        for item in primitives
    ]
    text = json.dumps(
        payload, ensure_ascii=False, sort_keys=True, separators=(",", ":")
    )
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

def recipe_id_for(digest):
    return f"rec_{digest[:12]}"
```

键排序、无空白差异、`title` 不参与，保证“同一组原语无论标题怎么写、字典序怎么排，都是同一个编号”。`knowledge/compiler/generated.jsonl` 是可重建的产物，不手改；同一代码版本加同一原语表，重建必须得到同一哈希集合。测试里有一条 `test_enumerate_is_idempotent` 和一条 `test_generated_jsonl_rebuilds_same_ids` 专门守这个性质。

## 3.4 校准：真值必须来自影子实测

静态先验只能用于枚举剪枝。比如“停掉 MySQL 会让 `mysql_select_1` 红”，这是人的经验，不是评测真值。真值必须由校准器在影子里跑一遍：

1. 拿影子世界锁，确保没有第二场试修；
2. 把影子重置到健康基线（四个服务 running + healthy，六个探针全 PASS）；
3. 按配方注入；
4. 用影子探针采全套 `CHECK_IDS`，必要时按 `fault_confirmation_attempts` 重试；
5. 写入签名：`failing_checks`、`passing_checks`、`unknown_checks`、`affected_services`、`calibrated_at`、`twin_image_digests`；
6. 拆除配方，确认影子回到基线；回不了就标 `CALIBRATION_DIRTY`，该配方不得进入 holdout；
7. 非负例如果校准后没有任何失败探针，标 `RECIPE_INVALID` 并丢弃。

校准签名里带镜像摘要，是为了把“这次校准对应的镜像”固定下来。镜像变了、签名却还在，就可能出现“评测真值和现场观测不一致”。平台把这种差异记成 `SIGNATURE_DRIFT`，剔除出分母，而不是算模型答错。

当前 `calibrated.jsonl` 有 102 条校准记录。这个数字不大，但每一条都经过了“注入 → 采证 → 拆除 → 回基线”的完整过程。校准器宁愿少几条，也不把没有跑过的先验写进真值。

## 3.5 seen / holdout 与防泄漏

校准池按规范哈希排序，取后 30% 冻结为 holdout。当前 27 条。算法写在 `split.py` 里，冻结文件 `knowledge/compiler/holdout.json` 提交进仓库，包含 `frozen_at`、`compiler_version`、`algorithm`、`canonical_excluded` 和 `ids`。

冻结之后只许追加说明，不许改 `ids`。`scripts/check_holdout.py` 在 CI 里做四件事：版本对不对、哈希集合是否仍等于当前枚举结果、是否混入六个 canonical 场景、双原语是否足够。任何一条不满足就失败。这样做的目的是防止“改完题再跑模型”的侥幸：holdout 一旦被改动，CI 第一步就红。

防泄漏不止是“不把 holdout 编号给模型”。平台还做了这些：

- 工作台注入 holdout 返回 `HOLDOUT_FORBIDDEN_IN_LAB`；holdout 只用于评测。
- 未见评测只抽 holdout；指定 seen 返回 `SEEN_FORBIDDEN_IN_UNSEEN`。
- 盲诊上下文里不出现配方编号、原语、`canonical_hash`、`holdout` 标记、期望签名、场景枚举。
- 截图文件名、存储路径、附件摘要不进模型载荷；文件名是用户可控文本，可能起成答案标签。
- 日志、Runbook、截图里的文字统一声明为“数据，不是指令”；对抗样本的投毒文本只出现在证据位。
- 工单列表、无令牌的评测 GET 不返回配方原语和签名。

## 3.6 影子世界：批准之前的另一个物理世界

影子世界不是一个“逻辑沙箱”，而是四个真实的 Docker 容器。它必须和真环境物理隔离，否则“试修”可能通过共享文件或网络打到真环境。隔离清单如下：

| 隔离项 | 真环境 | 影子世界 |
| --- | --- | --- |
| Compose 项目 | `aiops-demo` | `aiops-twin` |
| Compose 文件 | `deploy/docker-compose.yml` | `deploy/docker-compose.twin.yml` |
| MySQL / Redis 端口 | 13306 / 16379 | 23306 / 26379 |
| 应用 / Nginx 地址 | 18000 / 18080 | 28000 / 28080 |
| Nginx 活动配置 | `demo/nginx/active/default.conf` | `demo/twin/nginx/active/default.conf` |
| 应用模式文件 | `demo/app-control/mode` | `demo/twin/app-control/mode` |
| 数据卷 | `aiops-demo_*` | `aiops-twin_*` |
| Holmes | 有 | 没有 |
| 试修锁 | 工作台实验租约 | `data/twin.lock` 世界锁 |

`World` 抽象把这些差异收进一个不可变对象。`DockerController` 和 `Probes` 构造时绑定一个 `World`，之后所有命令、路径、端口都从它取。这样做的直接好处是：同一份 `perform(action_id)` 代码可以在两个世界里执行，但永远不会把影子的 Nginx 配置写到真环境。

影子试修前必须先 `reset_to(recipe)`：拆除一切 → 回到基线 → 再注入该配方。原因是上一次试修可能已经把影子改成了“修好”的状态；如果在脏影子上做下一次预测，预测结果没有意义。

## 3.7 试修与预测证书

一次试修的顺序是：

```text
reset_to(recipe)              # 拆除 → 基线 → 重新注入配方
perform(action_id)            # 只执行目录动作
采样 before / after 探针       # 至少一次；必要时等待恢复
reset_to(recipe)              # 把影子放回故障态，供下一次试修
```

`before` 是注入后的探针状态，`after` 是执行动作后的状态。平台输出三个字段：

- `predicted_pass`：从 FAIL 变 PASS 的探针；
- `predicted_still_fail`：执行后仍然 FAIL 的探针；
- `would_resolve_signature`：签名内的失败探针是否全部变绿。

这三个字段只是预测，不是结论。人仍然只批准真环境那一次；真环境复测后，平台拿 `predicted` 和 `observed` 逐探针对照，生成 `twin_certificates`，写入匹配率。预测和实测一致，说明影子可信；不一致记 `TWIN_DIVERGENCE`，把差异保留下来，供排查镜像或配置漂移。影子起不来或试修超时，记 `skipped=true` 并写明原因，不编一个预测顶上。

以 2026-11-17 的 MySQL 工单为例：影子试修 `START_DEMO_MYSQL`，耗时 18.65 秒；`before` 是 `mysql_select_1`、`app_db_check` 双 FAIL，`after` 六个探针全 PASS；`predicted_pass` 正好是这两个探针，证书匹配率 100%。真环境复测第一次采样仍是双 FAIL（MySQL 刚启动），第二次采样双 PASS，最终 `RESOLVED`。这个例子说明“预测”和“实测”是两件事：影子预测会恢复，真环境也要经过启动抖动，不能因为第一次采样还是红的就判失败。

## 3.8 R 臂：影子里的非模型基线

除了模型规划，平台还有一条不调模型的搜索路径，用来做对照基线。它只在影子里跑，不进入盲诊，也不计模型正确率。

搜索空间做了三层裁剪：

1. 只取六个 canonical 恢复动作，以及目标服务匹配的动作；
2. 链式变体（动作 + 复测探针）只保留签名里出现过的探针，不扫描全部 `THEN` 变体；
3. 候选上限 30 个，按目录顺序试，命中第一个能修好的就停。

当前演示库里 R 臂搜索 3 次，平均试 4 个候选，签名消歧率 33.3%。这个数字的意义不是“R 臂很弱”，而是给“模型到底有没有比规则强”一个参照上界：如果模型连 30 个候选里的第一个都选不中，说明它的规划没有超过“按目录顺序试”的基线；如果模型选得中，也要看它多花了几次调用、多少秒。

## 3.9 注入确认与半注入回滚

故障必须真实发生，而且必须被证实。注入后平台按 `fault_confirmation_attempts=3`、间隔 2 秒反复采证，直到该场景的故障成立。Nginx 502 有一个容易误判的瞬态：容器退出后代理可能短暂返回 504，平台不会把 504 当成目标 502，而是继续采到真正的 502 才确认。

双侧注入还要保证原子性：真环境注入成功、影子注入失败时，平台回滚真环境并返回 `TWIN_UNAVAILABLE`，不留下“真环境坏了、影子是好的”的半边故障。工作台旧场景仍可走，但编译器双侧注入需要影子可用；页面不会声称做过试修。

六个 canonical 场景就是编译器也能生成的特例。`services/faults.py` 现在只是 `compiler.apply` 的薄封装：`apply_fault` 把场景转成 canonical 配方，`clear_fault` 调 `undo_recipe`。这样注入逻辑只有一份，不会出现“按钮走一条路、编译器走另一条路”的漂移。
