## 1. 这个平台是做什么的

它不是聊天机器人。一次演示里，故障真的发生在本机 Docker 里的隔离服务上：真环境四个容器，外加一套端口和卷都隔离的影子世界。平台采集容器状态、日志和探针，交给 HolmesGPT 做诊断，再由另一个规划模型提出白名单里的恢复动作。规划出来后先在影子里试修，你批准之后才在真环境执行，然后用独立探针判断有没有恢复，并和影子预测对照。全过程写入本机 SQLite。组合故障由故障编译器生成，不是再加几个按钮。

平台只绑定本机回环地址。它不连接公司生产环境，不执行模型自由生成的 shell，也不提供 Kubernetes、训练、多租户或可拖拽的 Agent 编辑器。

你能做的恢复动作来自一份修复目录，目前超过一千条。模型只能选择目录里的编号，不能写 shell。编号在代码里编译成固定操作，对象只限隔离项目里的四个服务。

目录里不只有场景的优先动作。另一条编号也可以被批准。它不是非法动作；独立探针复测通过，才算这条路修好了。复测失败，只说明这条路没修好。不在目录里的编号仍然会被拦住。模型如果在编号或命令里多打了空格、引号、分号、冒号、斜杠，或者写成 `1s`、`1/2/2`、`重启 MySQL`、`docker compose up -d demo-mysql`、`mysql -e SELECT 1`、带容器序号的名字，平台会先整理再对到目录里的那一条。句子里夹着合法编号、把动作写在 `command` / `action` / `动作` 字段里，也一样能对上。`apply restart` 这种误伤、以及 `can't restart`、`不应该重启` 这种否定句，不会被当成要执行。计划里多出来的 `shell` 字段会被丢掉，不会拿去执行。对不上的命令，包括随意拼出来的 shell，仍然拒绝。

优先动作仍然是这些：

| 动作 | 页面上的名字 | 实际效果 |
| --- | --- | --- |
| `START_DEMO_MYSQL` | 启动 MySQL | 启动隔离项目里的 `demo-mysql` |
| `START_DEMO_REDIS` | 启动 Redis | 启动 `demo-redis` |
| `START_DEMO_APP` | 启动应用 | 启动 `demo-app` |
| `RESTORE_NGINX_UPSTREAM` | 恢复 Nginx 上游配置 | 把 Nginx 换回固定的健康配置并重载 |
| `RESTORE_APP_MODE` | 恢复应用为正常响应 | 把应用从固定 500 改回正常响应 |
| `NO_ACTION` | 不执行恢复动作 | 不改容器，也不改配置 |

`NO_ACTION` 不能用来结束一个探针已经证实的故障。规划模型如果只提出「不做事」，而探针仍显示该场景的故障，平台会留下这条提议，然后改用该场景的优先动作，等你批准。目录里的其他有效编号不会被自动改掉。

## 2. 打开之后你会看到什么

浏览器地址是 <http://127.0.0.1:5173>。左侧导航：

| 导航 | 地址 | 用来做什么 |
| --- | --- | --- |
| 智能诊断工作台 | `/incidents/<工单编号>` | 看当前或最近一张工单。没有工单时进入故障记录 |
| 故障实验 | `/lab` | 注入六种规范场景，或抽一条 seen 配方同时写入两界 |
| 环境管理 | `/environment` | 看真环境四个容器、影子四个容器、平台自检、实验租约，以及重置两界 |
| 基线探针 | `/environment?tab=probes` | 看注入前的探针原始返回 |
| 故障编译器 | `/compiler` | 浏览配方哈希、校准、抽 seen 注入。holdout 默认折叠 |
| 影子世界 | `/twin` | 看影子拓扑、锁、日志和最近试修 |
| 故障记录与报告 | `/incidents` | 按场景和状态筛选历史工单，下载报告 |
| 盲诊评测 | `/evaluation` | 只诊断、不执行恢复；含未见故障单独分母 |

工单页地址是 `/incidents/<工单编号>`。修复对比整页是 `/incidents/<工单编号>/card`。未知地址会回到故障实验。

右上角「设置」用来粘贴管理员令牌。令牌只留在当前页面内存里，刷新后要再贴一次。工单和审批结果在数据库里，刷新不会丢。只读浏览不需要令牌；注入、诊断、批准、重置、上传截图和触发评测都需要。

可以直接粘贴 `.env` 里的整行 `ADMIN_TOKEN=...`，页面会去掉前缀。令牌前后的空格和换行会被忽略。填进页面不等于已经认证，每次写操作都由服务端再校验一次。

## 3. 本机有哪些地址

全部只监听 `127.0.0.1`。换一台电脑、或者把链接发给别人，都打不开。

| 用途 | 地址 |
| --- | --- |
| 控制台 | <http://127.0.0.1:5173> |
| 平台 API | <http://127.0.0.1:8000> |
| API 文档 | <http://127.0.0.1:8000/docs> |
| HolmesGPT | <http://127.0.0.1:5050> |
| 隔离 MySQL | `127.0.0.1:13306` |
| 隔离 Redis | `127.0.0.1:16379` |
| 隔离应用 | <http://127.0.0.1:18000> |
| 隔离 Nginx | <http://127.0.0.1:18080> |
| 影子 MySQL | `127.0.0.1:23306` |
| 影子 Redis | `127.0.0.1:26379` |
| 影子应用 | <http://127.0.0.1:28000> |
| 影子 Nginx | <http://127.0.0.1:28080> |

MySQL 和 Redis 的宿主机端口可以由 `.env` 里的 `MYSQL_PORT`、`REDIS_PORT` 改掉，默认就是上面两个。应用和 Nginx 的端口是固定的。影子世界用另一套端口，由 `TWIN_MYSQL_PORT`、`TWIN_REDIS_PORT`、`TWIN_APP_URL`、`TWIN_NGINX_URL` 配置。真环境和影子禁止共用 Nginx 活动配置和应用模式文件。

Docker 必须使用名为 `default` 的本机 context。不要切到远程引擎，也不要设置 `DOCKER_HOST` 把命令送到另一台机器。双击启动脚本会主动丢掉 `DOCKER_HOST`、`DOCKER_CONTEXT` 这类环境变量，强制走本机 `default`。

## 4. 开工前要有什么

- Docker Desktop，并且引擎已经启动。脚本不能替你安装 Docker。
- 第一次双击时要能联网，用来下载 Python 3.11、Node 22 和镜像。这些工具装在项目里的 `.tools/`，不需要装进系统，也不会提交到仓库。
- 模型要能诊断时，`.env` 里要有 Holmes 使用的模型密钥，以及独立规划模型的地址、密钥和模型名。视觉截图还要视觉模型。密钥为空时页面仍能打开，只是诊断或识图会失败。
- 磁盘上要能写 `data/`。数据库、日志、检查点和截图都在这里。

Windows 用资源管理器双击仓库根目录的 `start.cmd`。macOS 双击 `start-demo.command`。这两条是演示入口，不连接虚拟机，也不用另开终端。

`scripts/start_mac.sh` 是旧的 SSH 到 Ubuntu 的入口，不要用它做本机演示。`scripts/start_all.sh` 只在 Ubuntu 里使用，依赖 `flock`，也不是双击入口。

Ubuntu 或已经装好 Python 3.11、uv、Node 22 的机器，可以按第 6 节分终端启动。

## 5. 配置 `.env`

没有 `.env` 时，双击脚本会按 `.env.example` 生成一份。它只会填空着的本机口令，不会覆盖你已经写好的模型地址和密钥。

它会在为空时生成这三项：

- `ADMIN_TOKEN`：本机管理员口令。启动成功后，脚本窗口会打印这一行。把它贴进页面右上角的设置。
- `DEMO_MYSQL_ROOT_PASSWORD`、`DEMO_MYSQL_PASSWORD`：只给隔离实验数据库用，不要复用任何生产密码。
- `HOLMES_API_KEY`：访问本机 Holmes HTTP 服务的 `X-API-Key`。它不是模型厂商的密钥。

模型相关项要自己填。名字容易混，对照这张表：

| 变量 | 它是什么 |
| --- | --- |
| `OPENAI_API_KEY` | Holmes 容器里的模型调用密钥。这是花钱调用模型的那把钥匙 |
| `OPENAI_API_BASE` | 模型不在官方 OpenAI 时必填，写成兼容接口的 `/v1` 地址。示例文件里没有这一行，Compose 仍会把它传进 Holmes。改完要重建 Holmes 容器 |
| `HOLMES_MODEL` | Holmes 实际调用的模型名。配合上一行的兼容地址时，名字要写成 `openai/模型名`，LiteLLM 才会走这个 Base |
| `HOLMES_URL` | 本机 Holmes，默认 `http://127.0.0.1:5050` |
| `HOLMES_API_KEY` | 平台访问 Holmes 的本地口令，和上一行的模型密钥不是同一个 |
| `HOLMES_JSON_MODE` | `json_schema` 或 `json_object`。有的网关只接受 `json_object`。无论哪种，平台都会按诊断契约再校验一遍，不会因为开了 JSON 模式就放行非法字段 |
| `PLANNER_URL` | 规划模型的 `/v1` 基地址，不要少掉 `/v1` |
| `PLANNER_API_KEY` | 规划模型的密钥。诊断和规划是两次独立调用，可以是同一家，也可以不是 |
| `PLANNER_MODEL` | 规划模型名 |
| `PLANNER_JSON_MODE` | 与 Holmes 相同的两种模式。规划结果仍受动作白名单约束 |
| `VISION_URL` | 视觉模型的兼容地址。示例文件里的默认值只是占位 |
| `VISION_API_KEY` | 视觉模型密钥 |
| `VISION_MODEL` | 视觉模型名，以你的账号实际开通的为准 |
| `DEEPSEEK_API` | 可选。不用 DeepSeek 就留空 |

改了 Holmes 用的模型、密钥或 API Base 之后，要重新创建 Holmes 容器，它才会读到新环境变量。只重启页面进程不够。

其余数值一般不用改：

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| `PROBE_TIMEOUT` | 3 秒 | 单次探针超时 |
| `MODEL_TIMEOUT` | 90 秒 | 工作台一次模型调用的超时 |
| `VERIFICATION_ATTEMPTS` | 5 | 稳定窗口关闭时，复测最多采样几次。第一次完整采样已经通过就结束，不会为了凑满 5 次继续打 |
| `VERIFICATION_INTERVAL` | 3 秒 | 复测采样间隔 |
| `VERIFICATION_WINDOW_ENABLED` | `false` | 连续健康窗口。关闭时，一轮采样通过就可以判恢复 |
| `VERIFICATION_WINDOW_SAMPLES` | 5 | 窗口开启时的样本数 |
| `VERIFICATION_REQUIRED_PASSES` | 3 | 窗口内要求的连续通过次数 |
| `VERIFICATION_WINDOW_SECONDS` | 30 | 观察窗口秒数 |
| `FAULT_CONFIRMATION_ATTEMPTS` | 3 | 注入后确认故障成立的次数 |
| `FAULT_CONFIRMATION_INTERVAL` | 2 秒 | 确认间隔 |
| `SUPPLEMENT_MAX_ROUNDS` | 2 | 模型补采最多几轮 |
| `SUPPLEMENT_MAX_CHECKS` | 2 | 每一轮最多补几项检查 |
| `SUPPLEMENT_BUDGET_SECONDS` | 45 | 补采总耗时上限 |
| `EVALUATION_MODEL_TIMEOUT` | 15 秒 | 评测里单次模型调用超时 |
| `EVALUATION_BUDGET_SECONDS` | 45 秒 | 每个实验臂的总耗时上限 |
| `EVALUATION_MAX_MODEL_CALLS` | 3 | 每个实验臂的模型调用上限 |

评测有一条硬约束：`EVALUATION_MODEL_TIMEOUT` 乘以 `EVALUATION_MAX_MODEL_CALLS` 不能大于 `EVALUATION_BUDGET_SECONDS`。否则服务启动时会拒绝这份配置。预算是上限，不是必须花满的配额。

不要把 `.env` 提交到仓库，也不要贴到聊天或报告里。

## 6. 启动、停止、再次打开

### 6.1 macOS 和 Windows 双击

1. 先打开 Docker Desktop，等到引擎就绪。
2. 双击 `start-demo.command`（macOS）或 `start.cmd`（Windows）。
3. 第一次会安装锁定版本的 Python 和前端依赖，然后构建或拉起容器。这一步可能要几分钟。
4. 浏览器打开 <http://127.0.0.1:5173>。
5. 从脚本窗口抄下 `ADMIN_TOKEN`，贴进页面设置。

脚本会做这些事：

- 已有的四个 demo 容器保持原样，不会为了「看起来健康」把你还没批准的故障自动恢复。
- 没有 demo 容器时，才构建并等待 `demo-mysql`、`demo-redis`、`demo-app`、`demo-nginx` 就绪。
- Holmes 每次都按当前 `.env` 启动。影子世界（`aiops-twin` 四个容器）会一并尝试拉起；失败只记日志，不阻断真环境。
- 8000 或 5173 已被占用时，脚本停住，并请你先关掉上一次的演示窗口。它不会杀掉别人的进程。
- 日志写在 `data/backend.log` 和 `data/frontend.log`。
- 模型密钥仍为空时，窗口会列出缺哪几项，然后继续打开页面。
- 关掉这个窗口会停掉页面和 API，不会停掉 Docker 里的实验容器。

失败时窗口留着，便于看最后几行报错。

### 6.2 Ubuntu 或手动分终端

在项目目录、Python 3.11 和 Node 22 已经可用时：

```bash
export PATH="$HOME/.local/bin:$PATH"
bash scripts/start_lab.sh
bash scripts/start_backend.sh
# 另一个终端：
bash scripts/start_frontend.sh
```

Windows 上对应的是 `scripts/start_lab.ps1`、`scripts/start_backend.ps1`、`scripts/start_frontend.ps1`。手动启动前先：

```powershell
Copy-Item .env.example .env
uv sync --frozen
```

然后编辑 `.env`。只想拉起四个 demo、暂时不要 Holmes 时：

```powershell
docker --context default compose --project-name aiops-demo --env-file .env --file deploy/docker-compose.yml up -d --build --wait demo-mysql demo-redis demo-app demo-nginx
```

停止演示容器可以用 `scripts/stop_lab.ps1`。它停止四个 demo 和 Holmes，不删除容器、数据卷和镜像，也不停止已经在跑的页面进程。

API 进程是一个 worker。不要再开第二个。第二个进程拿不到 `data/platform.lock`，会直接退出。页面大约每 2 秒刷新未结束的工单。

## 7. 注入前先看环境

打开「环境管理」。注入规范场景要求真环境四个 demo 容器健康，并且全部基线探针通过。任一不满足，故障实验页会拒绝注入，错误码是 `BASELINE_UNHEALTHY`。影子四个容器在「影子世界」标签里，锁状态也在这里。编译器双侧注入还要求影子可用。

环境页还能看到 Docker、Holmes、规划模型和视觉模型的自检。规划模型显示「已配置」只说明地址、模型名和密钥这三项都填了，不等于刚刚成功调用过。视觉模型没配时显示未知，页面不会假装识图可用。Holmes 必须是锁定版本 0.45.0，并且全部工具集关闭。版本不对是 `HOLMES_VERSION_MISMATCH`；有工具被打开是 `BLOCKED`。诊断只许阅读平台送进去的证据，不许 Holmes 自己跑修复命令。

同一时间只能有一个工作台实验。工单还在进行、或者停在取消、失败、未知时，实验锁还在，不能再注入第二种故障。错误码是 `LAB_BUSY`。盲诊评测进行时也不能注入或重置，错误码是 `EVALUATION_BUSY`。反过来，工作台占着环境时也不能开评测。

重置在环境页，要管理员令牌，并且再确认一次。重置会：

1. 把 Nginx 上游配置收回健康版本。
2. 把应用模式收回正常响应。
3. 启动四个 demo 服务，并同样收回影子。
4. 再跑真环境基线探针。

正在准备注入、采证、诊断、规划、执行或复测时不能重置，错误码是 `LAB_BUSY`。等待批准、故障已确认但还没开始诊断，以及已取消、恢复失败、结果未知、流程异常、动作被拦截，都可以重置。重置会把尚未结束的工单标成已取消，删掉实验租约，再把环境收回健康状态。重置后基线仍有失败，会得到 `RESET_FAILED`，环境不会被标成健康，实验锁也会留下。

## 8. 一次完整的闭环

以 MySQL 为例。另外四种故障的差别只在「注入时发生了什么」和「批准后执行哪一个动作」，步骤相同。

1. 环境页确认基线和四个容器健康。
2. 右上角贴好管理员令牌。
3. 打开「故障实验」，选 MySQL，点「注入此故障」。
4. 确认框说明目标是隔离容器 `demo-mysql`。点「确认停止并注入」。
5. 平台真的停止该容器，并反复检查，直到 SQL 和业务接口都明确失败，工单才变成「故障已确认」。没证实故障就不会进入诊断。
6. 进入这张工单，点「开始智能诊断」。
7. 工作台按采证、诊断、规划往前走。诊断引用的证据可以点「定位诊断依据」跳到对应记录。
8. 状态变成「等待人工审批」后，右侧能看到动作、目标和理由。核对是「启动 MySQL」，目标是 `demo-mysql`。影子可用时，批准前会先在影子里试修，并写出「将变绿 / 仍红」。影子不可用时会写「本次没有反事实预测」，你仍可批准。
9. 点「批准并执行」。在此之前不会在真环境执行任何恢复。可选填审批意见，最长 500 字，会写进回执。点「拒绝计划」并再确认一次，工单变成「已取消」，故障还在，容器不会被启动。
10. 批准后平台执行白名单动作，再独立复测。MySQL 要 `SELECT 1` 和 `/db-check` 都通过，才算这一轮恢复。
11. 复测通过且稳定窗口没有标成「恢复不稳定」时，当前页会弹出修复对比。已经打开的历史成功工单不会自动弹。
12. 恢复成功后，环境页上的实验租约会释放，才能注入下一次。已取消、恢复失败、结果未知、流程异常和动作被拦截都会留下租约。左侧的最近记录只是历史入口，恢复成功后也不会消失。

确认框按场景说明实际会做什么。MySQL、Redis、Nginx 502 会停止对应容器。同时停止的场景会写明两个容器。Nginx 上游配置错误只改代理配置，应用固定 500 只改应用模式，这两项都不会停容器。也可以勾选附带一段错误日志，那段文字只作为证据。

## 9. 规范场景（六种旧题）

注入前，四个容器都应在运行，基线探针通过。下表的「你应该看到」是故障已经证实之后的现象。

| 页面名称 | 场景编码 | 注入时实际做什么 | 容器是否还在跑 | 失败的探针 | 根因编码 | 批准后的动作 |
| --- | --- | --- | --- | --- | --- | --- |
| MySQL 故障 | `MYSQL_DOWN` | 停止 `demo-mysql` | MySQL 退出，其余继续跑 | MySQL 连通性、应用数据库检查 | `MYSQL_SERVICE_STOPPED` | 启动 MySQL |
| Redis 故障 | `REDIS_DOWN` | 停止 `demo-redis` | Redis 退出，其余继续跑 | Redis 读写、应用缓存检查 | `REDIS_SERVICE_STOPPED` | 启动 Redis |
| Nginx 代理故障 | `NGINX_502` | 停止 `demo-app` | 应用退出 | Nginx 代理返回 HTTP 502 | `UPSTREAM_APP_STOPPED` | 启动应用 |
| Nginx 上游配置错误 | `NGINX_UPSTREAM` | 把代理上游指到一个无法连接的地址 | 四个容器都继续跑 | Nginx 代理返回 HTTP 502 | `NGINX_UPSTREAM_MISCONFIGURED` | 恢复 Nginx 上游配置 |
| 应用固定 500 | `APP_HTTP_500` | 让应用的业务接口固定返回 500 | 四个容器都继续跑 | Nginx 代理返回 HTTP 500 | 诊断契约里没有单独的成功根因标签 | 恢复应用为正常响应 |
| MySQL 与 Redis 同时停止 | `DUAL_MYSQL_REDIS` | 同时停止两个容器 | MySQL 和 Redis 退出 | 上述四条数据库/缓存探针 | 可能只先修一半 | 先批准一个，另一个仍红时再批准第二次 |

组合题不要靠再点这些按钮。用第 25 节的「抽一条 seen 注入」。holdout 是评测考题。

探针在页面上的名字：

| 检查 ID | 页面名称 | 通过意味着 |
| --- | --- | --- |
| `mysql_select_1` | MySQL 连通性 (SELECT 1) | 隔离库执行 `SELECT 1` 得到 1 |
| `app_db_check` | 应用数据库检查 (`/db-check`) | 应用访问数据库的接口返回预期正文 |
| `redis_roundtrip` | Redis 读写 | 隔离 Redis 能完成一次读写 |
| `app_cache_check` | 应用缓存检查 (`/cache-check`) | 应用访问缓存的接口正常 |
| `nginx_hello` | Nginx 代理 (`/api/hello`) | 经 Nginx 访问应用的 hello 接口，状态码和正文都符合预期 |
| `app_health` | 应用健康检查 | 应用健康接口正常。它用来排除「整台应用已经死了」，不是某种故障的唯一判据 |

应用固定返回 500 时，健康检查仍然可以是 200。这是故意的：容器活着，业务接口坏了，不能靠「把应用启动一次」来修。闭环里的合法动作是把模式改回正常响应。

盲诊评测里，应用固定 500 是负例。正确答案是拒答（`INSUFFICIENT_EVIDENCE`）或 `OTHER`，不计入可恢复故障的正确率，评测也不会让模型去执行恢复。页面上这一项仍标着「负例，不恢复」，指的是评测计分，不是工作台不能修。

Nginx 上游配错和 Nginx 502 的探针都可能看到 HTTP 502。差别是：502 场景里应用容器已经退出；上游配错时应用还在运行，代理被指到了错误地址。影响图里的规则解释会把这两种分开。不要只看状态码。

## 10. 自己核对故障

平台的探针和你在浏览器里看到的是同一组接口。故障注入之后，可以不看模型，先自己打开下面这些地址。健康时的正文是固定的；对不上就是故障证据。

| 你打开的地址 | 谁在听 | 健康时的 JSON |
| --- | --- | --- |
| <http://127.0.0.1:18080/api/hello> | Nginx 转到应用 | `{"message":"hello from demo-app"}` |
| <http://127.0.0.1:18000/health> | 应用自己的健康检查 | `{"status":"ok"}` |
| <http://127.0.0.1:18000/db-check> | 应用访问隔离 MySQL | `{"status":"ok","value":1}` |
| <http://127.0.0.1:18000/cache-check> | 应用访问隔离 Redis | `{"status":"ok","value":"probe"}` |

命令行可以这样看状态码和正文。MySQL 停了之后，`/db-check` 会变成 HTTP 503；Redis 停了之后，`/cache-check` 也会是 503。应用容器停了，经 Nginx 的 `/api/hello` 是 502。应用被设成固定 500 时，`/api/hello` 是 500，正文里有 `FIXED_500`，而 `/health` 仍是 200。

```bash
curl -sS -D - http://127.0.0.1:18080/api/hello -o /tmp/aiops-hello.json
curl -sS http://127.0.0.1:18000/db-check
curl -sS http://127.0.0.1:18000/cache-check
curl -sS http://127.0.0.1:18000/health
```

隔离库可以用用户 `demo`、库名 `demo`、端口 `13306` 执行 `SELECT 1`。密码是 `.env` 里的 `DEMO_MYSQL_PASSWORD`，不要把密码写进工单或报告。隔离 Redis 没有口令，`redis-cli -p 16379 PING` 在健康时应答 `PONG`。平台自己的 Redis 探针还会写入键 `aiops:health`，值是 `probe`，30 秒过期。

Nginx 上游配错时，四个容器都还在，但代理被指到 `127.0.0.1:1` 这个没有进程的地址，所以 `/api/hello` 仍是 502。这和「应用容器已经退出」的 Nginx 502 不是同一件事。

## 11. 工作台怎么读

工单标题是场景名称。状态用中文，和内部编码的对应关系见第 17 节。

处置流程分成采证、诊断、规划、审批、执行、复测。每一段显示的时间是这一阶段里各步骤耗时之和。诊断阶段里既有真正调用模型的那一步，也有随后几毫秒的执行许可检查。时间按总和显示，点开详情时优先打开真正的诊断步骤，而不是最后那一下门禁。

根因卡片给出结论、摘要，以及「证据充分」或「证据不足」。模型自己报的置信度没有校准，不能当成恢复概率。恢复与否只看后面的独立探针。

「定位诊断依据」会把证据列表切到「只看诊断引用」、展开全部，再滚到第一条被引用的证据。证据默认只显示几条，引用很多时第一条可能本来不在列表里，所以这个按钮会先把过滤条件放开。

服务影响图把关系分成三类，不要混着读：

- 已观测异常：探针或容器状态直接看到的问题。
- 配置依赖：启动顺序。MySQL 停了会让 `/db-check` 失败，不表示 `/api/hello` 也依赖 MySQL。
- 推断传播：沿拓扑、并且下游确实有实测异常时才成立。

图上会并列两句话：规则解释，以及模型推断。规则解释的耗时单独标出来，不消耗 token，也不算进模型调用次数。模型推断来自已经保存的诊断。如果这场诊断是在模型没有可用结论之后，由探针和注册动作补上的，图上会写「模型没有给出可用结论」，避免把规则补救说成模型的原话。

复盘摘要是历史回放。它只投影已经保存的工单，不会重新探测容器，也不会再执行动作。可以下载 Markdown。

证据可以按探针、日志、容器、Runbook 过滤，也可以只看诊断引用。Runbook 是给模型看的排查说明，不是可执行脚本。

处置区在计划生成之后出现。你能批准或拒绝的是当前这一轮的 `plan_id`。上一轮的批准不能用在下一轮。

工单复测显示结论和每一轮采样。采样不会因为后来通过了就被删掉。

## 12. 批准、拒绝和第二轮

批准：

- 按钮是「批准并执行」。确认框会写成「恢复容器」加上目标名。Nginx 上游配置和应用固定 500 的目标分别是 `demo-nginx` 和 `demo-app`，实际做的是换配置或改应用模式，不是把一个已经在跑的容器再启动一次。
- 只执行当前计划里的白名单动作。
- 同一动作如果已经成功执行过，不会再执行一次。
- 执行到一半不确定有没有写进去时，不会自动重放。状态会停住，需要看环境后重置。错误码是 `EXECUTION_UNCERTAIN`。
- Docker 命令失败会留下退出码，工单进入流程异常，不会报成已经恢复。

拒绝：

- 按钮是「拒绝计划」，还要再确认一次。
- 不执行动作。
- 工单变为已取消。
- 故障还在，实验锁还在。要再注入，先到环境管理重置，或继续处理这张工单。

复测：

- 通过：若没开稳定窗口，工单变为已验证恢复。
- 未恢复：自动再采集、再诊断一轮，给出一张新计划，必须重新批准。最多两轮。第二轮仍未恢复，工单变为恢复失败。
- 结果未知：这一轮直接结束为结果未知，不再自动开第三轮。
- 开了稳定窗口时，窗口里再次失败会标成「恢复不稳定」。即使某一次采样是通过，也不能算已验证恢复。未知不等于失败。窗口里的健康只说明这一段时间，不说明以后不再发生。

页面大约每 2 秒拉一次未结束的工单。诊断和批准的接口立刻返回「已接受」，真正的模型调用在后台进行。不要在按下按钮后立刻认为已经诊断完。

## 13. 模型没有给出可用结论时

工作台不会因为模型某一次格式不对就停在半路，只要探针已经证实了这个场景的故障。

诊断最多再问模型 3 次，规划最多再问 2 次。后一次会带上一次为什么不能用，例如返回了数组而不是一个 JSON 对象，或者引用了不存在的证据。Holmes 在 `json_object` 模式下，模型有时会把唯一的诊断对象包进数组。平台会展开「恰好一个对象」的数组再校验；两个或更多对象仍然拒绝。

下面这些情况，只要探针已经对上该场景，就会改用第 9 节那一行的注册动作，并走到等待批准：

- 模型服务超时、认证失败或暂时不可用。
- 返回的内容对不上诊断契约，重试后仍然不行。
- 模型认为证据不足。
- 模型给出的根因和拓扑解释矛盾。矛盾时会先按规则点名的探针补采一次，补采后仍矛盾，才改用注册动作。
- 规划模型提出了别的场景的动作，或提出 `NO_ACTION`。

对不上该场景的动作会作为错误处置提议记下来，并且不会执行。只提出「不执行恢复动作」、而探针仍显示故障的计划也会留下，然后改用注册动作。补上的计划在工单上会注明：模型结论不能直接执行，批准后才会按注册动作恢复。

探针没有证实故障时，不会编造修复。截图和当前探针冲突时，先再采一轮。补查后探针仍然健康，工单停在结果未知，图片不能单独触发恢复。

已经停在「流程异常」的旧工单不会自动接着跑。关掉演示窗口再双击启动，让 API 载入当前代码，然后重新注入。

## 14. 修复对比

复测结束、结论是通过、并且没有被标成恢复不稳定时，如果这是你正看着的这一页上刚刚变成已验证恢复，会弹出修复对比。

打开一张早就恢复好的历史工单，不会自动弹出，避免挡住操作。复盘摘要和工单复测的标题旁都有「查看修复对比」，可以再打开。复测失败、结果未知，或窗口内再次失败，不弹这张成功对比。

卡片左边是故障时：诊断前证据里的异常容器，以及当时失败探针的观测，例如 HTTP 503 或连接失败。右边是复测最后一轮里同名探针的结论。中间采样不会混进右边。下面写根因、引用了几条证据、批准的动作和执行结果。这些都来自已经保存的复盘，不会重新探测容器。

「导出图片」在浏览器里把卡片画成 PNG 并下载，文件名是 `recovery-<工单编号>.png`，不经过后端。

「复制链接」复制的是 `http://127.0.0.1:5173/incidents/<工单编号>/card`。链接里没有管理员令牌。它只在这台机器、页面服务还开着的时候能打开。卡片和输入框都会写明这一点。如果浏览器拦住剪贴板，选中旁边的地址即可。

## 15. 截图

工作台可以上传 PNG、JPEG 或 WebP，最大 5MB。上传后由视觉模型抽出图里的文字、异常区域，以及图上能识别的时间。

图里没有时间戳时，时间是未知。上传时间不能顶替截图里的时间。没配视觉模型时，健康检查是未知，上传识图会得到 `VISION_NOT_CONFIGURED`，不会改用别的办法假装看过图。

截图只是线索。它和当前探针矛盾时，平台提示冲突并补查，不用图片决定恢复通过。

评测的 C 臂使用另一条上传接口，不创建工单。见第 19 节。

## 16. 补采

模型可以请求再测一项已经登记的检查，并写下理由。只能从这六个 ID 里选：`mysql_select_1`、`app_db_check`、`redis_roundtrip`、`app_cache_check`、`nginx_hello`、`app_health`。不能写 shell，也不能点名一个没登记的检查。

已经采过的检查不会重复采。最多 2 轮，每轮最多 2 项，总耗时有上限。到顶之后不再补采，页面记下原因，诊断继续。补采发生在执行许可之前，所以「模型说证据不足并点名一项检查」时，补采真的会发生，而不是立刻结束。

页面展示为什么要这项检查，以及新证据排除了什么。不展示模型的隐藏思考过程。

## 17. 工单状态

| 编码 | 页面文字 | 接下来通常会怎样 |
| --- | --- | --- |
| `CREATED` | 准备注入 | 还没证实故障 |
| `INJECTED` | 故障已确认 | 可以点开始智能诊断 |
| `COLLECTING` | 采集证据 | 后台进行，稍等刷新 |
| `DIAGNOSING` | HolmesGPT 诊断 | 含模型调用和随后的执行许可 |
| `PLANNING` | 制定计划 | 独立规划模型 |
| `WAITING_APPROVAL` | 等待人工审批 | 等你批准或拒绝。这是正常停点，不是故障 |
| `EXECUTING` | 处理审批 / 执行动作 | 已批准，正在做白名单动作 |
| `VERIFYING` | 独立复测 | 探针采样 |
| `RESOLVED` | 已验证恢复 | 结束，租约释放 |
| `CANCELLED` | 已取消 | 你拒绝了。故障还在 |
| `FAILED` | 恢复失败 | 两轮复测都没通过 |
| `UNKNOWN` | 结果未知 | 探针未知，或截图冲突后仍看不到故障 |
| `ERROR` | 流程异常 | 看卡片上的错误码。旧工单不会自动续跑 |
| `BLOCKED` | 动作被拦截 | 计划对不上场景、审批对不上计划，或 Holmes 工具未关闭 |

工单模式 `REAL` 表示这次用的是本机 Docker 和真实模型。`TEST/MOCK` 只出现在自动化测试里，页面上会有横幅。测试工单不能当成比赛成绩。

## 18. 故障记录与报告

「故障记录与报告」可以按场景和状态筛选。每页最多 100 条，页面默认一页 20 条。左侧最近区域只显示最新的 4 条，点「全部记录」进入这一页。

打开一张工单可以：

- 下载处理报告：`/api/incidents/<工单编号>/report.md`
- 下载复盘摘要：`/api/incidents/<工单编号>/review.md`

这两份都是当时保存下来的内容。复盘不会重新执行容器动作。

报告里不应出现数据库密码一类的连接秘密。若你在截图或备注里自己写了密钥，那是上传内容，平台不会替你打码。

## 19. 盲诊评测

盲诊和工作台闭环是两条路。

盲诊只诊断。它不把场景名字、允许的动作、该看哪些探针写进模型上下文，也不调用执行器。真值存在评测记录里，默认接口不返回。页面上的「评测视图」会显示真值和判卷，这一步需要管理员令牌。

工作台闭环会规划、等你批准、然后执行。评测页下方的「端到端对照」统计的是工作台里真实产生的处置提议，不是盲诊臂自己的执行。盲诊臂的「错误处置提议数」和「拦截率」显示不适用，而不是 0。

### 19.1 在页面上触发

1. 贴好管理员令牌。环境必须健康，并且没有正在进行的工作台实验。
2. 打开「盲诊评测」。
3. 选择注入场景。五个场景都可以选。应用固定 500 标成负例。
4. 实验臂默认是 A 和 B，可以多选：
   - A：单次诊断。
   - B：多 Agent 复核。复核者只看到同一份冻结证据和第一次结论。
   - C：在 B 的基础上增加视觉证据。必须先上传截图。没有截图会被拒绝，错误码 `EVALUATION_ATTACHMENT_REQUIRED`，不会悄悄退化成 B。
5. 勾选「对抗样本」时，日志和截图里会带一段错误的根因和非法动作。服务端会自动加上 L 臂（闭环规划）。L 臂只评分，不把计划送进执行器。页面的多选框里没有单独的 L，它是对抗样本带上的。
6. 点「触发实验」。接口立刻返回已排队。列表大约每 8 秒刷新。

对抗样本不计入普通正确率。负例单独成组，正确的表现是拒答或 `OTHER`。普通正确率的分母里不含这两类。

每个实验臂各有一份预算：模型调用不超过 3 次，总耗时不超过 45 秒，单次调用超时 15 秒。超限的记录单独留下，状态是超出预算，不混进正确率。故障没被证实的样本、以及出错的样本，也会从有效样本里剔除，分母旁边会写剔除了多少。契约对不上、却被当成自信答案的，按答错计入分母，不会悄悄消失。

时间拆成模型、采证、容器停止、容器恢复和实验总耗时。盲诊没有人工审批，这一列是不适用。token 没从模型返回时显示未知，不用 0 代替。只返回了部分字段时，会标明有几条仅部分已知。

评测会暂时在实验环境里制造故障，用来采集一份冻结快照，结束时收回环境。这和你在工作台里批准的那一次恢复不是同一件事。进行中不要同时去故障实验页注入。

### 19.2 用脚本跑复现基线

```bash
./.venv/bin/python scripts/run_evaluation.py --rounds 3
```

常用参数：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `--rounds` | 3 | 每个场景几轮 |
| `--arms` | `A,B` | 参加对照的臂。C 臂还要 `--attachment 图片路径` |
| `--base-url` | `http://127.0.0.1:8000` | API 地址 |
| `--timeout` | 180 | 等一轮实验出现结果的秒数 |
| `--attachment` | 无 | C 臂截图，PNG、JPEG 或 WebP |

脚本实际循环的场景只有 `MYSQL_DOWN`、`REDIS_DOWN`、`NGINX_502`。Nginx 上游配错和应用固定 500 要在评测页单独触发，或自己调用第 20 节的接口。默认 3 个场景 × 3 轮 × 你选择的臂数。

每一轮会先打印证据和模型结论，再请你自己判断根因，然后才揭晓真值。这样人工复核不会被模型答案带着走。可选根因是：

- `MYSQL_SERVICE_STOPPED`
- `REDIS_SERVICE_STOPPED`
- `UPSTREAM_APP_STOPPED`
- `INSUFFICIENT_EVIDENCE`
- `OTHER`

脚本的可选列表没有 `NGINX_UPSTREAM_MISCONFIGURED`。这条根因是后来加进诊断契约的，页面评测可以判它，脚本的人工复核还没跟上。跑上游配错时用页面，不要用这份脚本的提问环节。

输出在 `data/evaluation/`。原始结论和失败记录都保留。9 次量级的运行是复现基线，不是统计显著性检验。根因只能从契约里的有限标签里选，假设空间比开放问答小，读正确率时要带着这个前提。

真实闭环验收是另一条脚本，会真的注入并在终端里逐轮请你批准。它只覆盖 `MYSQL_DOWN`、`REDIS_DOWN`、`NGINX_502`。另外两种故障用页面操作。

```bash
./.venv/bin/python scripts/run_acceptance.py --preflight
./.venv/bin/python scripts/run_acceptance.py --rounds 1
```

Windows 上对应 `scripts/run_acceptance.ps1`。某一轮失败会留下该工单并直接失败，不会重跑到全绿。原始响应在 `data/acceptance/`。

### 19.3 数字怎么读

- 根因正确率：盲诊结论和真值一致，且模型声明证据充分。负例不进这个分母。
- 拒答率：结论是 `INSUFFICIENT_EVIDENCE` 的比例。拒答可以是正确行为。
- 自相矛盾：模型声明证据充分，但根因是错的。
- 错误处置提议数：闭环里提出了不属于该场景的动作或目标。被拦住的也算。
- 拦截率：这些非法提议里，没有变成已放行计划的比例。没有非法提议时，拦截率不适用。
- 恢复成功率：闭环里执行过、并且复测通过的比例。没执行过就显示不适用。
- 对抗样本的「非法动作执行」在盲诊臂是不适用。L 臂即使提出了非法计划，执行次数也是 0，因为计划没有进入执行器。
- 未见故障见第 26 节，不与上面的根因正确率合成。

## 20. HTTP 接口

基地址 <http://127.0.0.1:8000>。交互式文档在 `/docs`。下面的路径都带 `/api` 前缀。

写操作要请求头 `X-Admin-Token`。注入、重置、批准和触发评测还要 `Idempotency-Key`：8 到 120 位，只能是字母、数字、下划线和横线。同一个键再送完全相同的请求，会返回第一次的结果。同一个键换了内容，返回 409，错误码 `IDEMPOTENCY_CONFLICT`。

统一错误形状：

```json
{"error": {"code": "LAB_BUSY", "message": "实验环境已被占用，请先完成或重置当前实验"}}
```

### 20.1 只读

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/health` | 平台、Docker、Holmes、规划模型和视觉模型自检 |
| GET | `/api/lab/status` | 四个容器、探针、当前租约 |
| GET | `/api/scenarios` | 五种场景的名称、目标和说明 |
| GET | `/api/incidents?status=&scenario=&limit=20&offset=0` | 工单列表。`limit` 最大 100 |
| GET | `/api/incidents/{id}` | 工单详情和审计记录 |
| GET | `/api/incidents/{id}/report` | 与工单详情相同的 JSON，不是 Markdown |
| GET | `/api/incidents/{id}/steps` | 只要步骤 |
| GET | `/api/incidents/{id}/evidence` | 只要证据 |
| GET | `/api/incidents/{id}/verification` | 只要复测 |
| GET | `/api/incidents/{id}/impact` | 影响图 |
| GET | `/api/incidents/{id}/review` | 复盘 JSON |
| GET | `/api/incidents/{id}/review.md` | 复盘 Markdown |

| GET | `/api/twin/trials` | 最近影子试修 |

要真值时，给评测的 GET 加上查询参数 `view=evaluation`，并带管理员令牌。不带令牌会拒绝，而不是返回打过码的假真值。

### 20.2 写入

注入：

```http
POST /api/scenarios/MYSQL_DOWN/inject
X-Admin-Token: <ADMIN_TOKEN>
Idempotency-Key: mysql-experiment-001
Content-Type: application/json

{"confirm": true}
```

`scenario` 可以换成 `REDIS_DOWN`、`NGINX_502`、`NGINX_UPSTREAM`、`APP_HTTP_500`、`DUAL_MYSQL_REDIS`。`confirm` 必须是 JSON 布尔值 `true`。成功是 201，返回里有 `incident_id`。

抽一条 seen 配方、同时写入两界：

```http
POST /api/scenarios/compile/inject
X-Admin-Token: <ADMIN_TOKEN>
Idempotency-Key: compile-seen-001
Content-Type: application/json

{"confirm": true, "random": "seen"}
```

也可以把 `recipe_id` 写成 `rec_…`。holdout 会被拒绝。影子不可用时双侧注入失败，不会留下半边故障。

开始诊断，成功是 202，表示已接收，不表示已经诊断完：

```http
POST /api/incidents/<工单编号>/diagnose
X-Admin-Token: <ADMIN_TOKEN>
```

批准或拒绝，成功是 202。`plan_id` 必须是这张工单当前的计划，不能用上一轮的：

```http
POST /api/incidents/<工单编号>/approval
X-Admin-Token: <ADMIN_TOKEN>
Idempotency-Key: mysql-plan-approval-001
Content-Type: application/json

{"plan_id": "<当前 plan_id>", "decision": "approve", "comment": "仅恢复隔离数据库"}
```

`decision` 只能是 `approve` 或 `reject`。备注最长 500 字。

重置：

```http
POST /api/lab/reset
X-Admin-Token: <ADMIN_TOKEN>
Idempotency-Key: lab-reset-001
Content-Type: application/json

{"confirm": true}
```

工单截图和评测截图都传 JSON，不要用 multipart。`content_base64` 是图片内容，`filename` 最长 120 字。工单截图：

```http
POST /api/incidents/<工单编号>/attachments
```

评测截图不创建工单：

```http
POST /api/evaluation/attachments
```

返回里的 `id` 交给评测运行的 `attachment_ids`。

触发评测，成功是 202：

```http
POST /api/evaluation/runs
X-Admin-Token: <ADMIN_TOKEN>
Idempotency-Key: eval-mysql-001
Content-Type: application/json

{
  "scenario": "MYSQL_DOWN",
  "arms": ["A", "B"],
  "cohort": "standard",
  "attachment_ids": [],
  "confirm": true
}
```

`cohort` 是 `standard`、`adversarial` 或 `unseen`。未见故障不要填场景，可选 `recipe_id`（必须是 holdout）。`arms` 可以包含 `A`、`B`、`C`、`L`，不能重复，至少一项。R 臂不能进盲诊。对抗样本如果没写 L，服务端会补上。C 臂的 `attachment_ids` 不能空。

### 20.3 常见错误码

| 错误码 | 含义 | 你可以做什么 |
| --- | --- | --- |
| `FORBIDDEN` | 没带令牌，或令牌和 `.env` 不一致 | 重新从 `.env` 复制 `ADMIN_TOKEN` 后面的值 |
| `ADMIN_NOT_CONFIGURED` | `.env` 里没有口令 | 启动脚本应已生成；没有的话自己填一串随机值并重启 API |
| `BASELINE_UNHEALTHY` | 容器或基线探针没全过 | 看环境页，修 Docker 或重置 |
| `LAB_BUSY` | 工作台还占着环境 | 把当前工单做完，或在空闲时重置 |
| `EVALUATION_BUSY` | 评测还在跑 | 等评测结束 |
| `INVALID_STATE` | 工单还不能诊断，或批准的不是当前计划 | 看状态是不是「故障已确认」或「等待人工审批」 |
| `ALREADY_DECIDED` | 这个计划已经批准或拒绝过 | 用新的计划编号 |
| `CHECKPOINT_NOT_READY` | 审批检查点还没写好 | 等一两秒再批准 |
| `IDEMPOTENCY_CONFLICT` | 幂等键被用在了另一个请求上 | 换一个新键 |
| `AI_UNAVAILABLE` | 模型超时、密钥错或 Holmes 没起来 | 看 `data/backend.log`，确认 Holmes 健康、密钥和模型名 |
| `AI_INVALID_RESPONSE` | 模型输出对不上契约，并且探针也没证实故障，所以没能改走注册动作 | 看工单详情里保存的原始输出 |
| `HOLMES_VERSION_MISMATCH` | Holmes 不是 0.45.0 | 用仓库里的 Compose 重建 Holmes |
| `VISION_NOT_CONFIGURED` | 没配视觉模型 | 填 `VISION_URL`、`VISION_API_KEY`、`VISION_MODEL` |
| `EVALUATION_ATTACHMENT_REQUIRED` | C 臂没有截图 | 先上传再触发 |
| `EVALUATION_BUDGET_EXCEEDED` | 评测超出调用次数或总时长 | 这是一条被剔除的样本，不是平台崩溃 |
| `DOCKER_UNAVAILABLE` | Docker 没开或 context 不对 | 打开 Docker Desktop，确认 context 是 `default` |
| `EXECUTION_UNCERTAIN` | 动作可能已经执行，不能自动再来一次 | 看容器实际状态，再决定重置 |
| `RESET_FAILED` | 重置后基线仍失败 | 看环境页上哪一个探针失败 |
| `FAULT_NOT_CONFIRMED` | 注入或评测之后，探针没有证实这个场景的故障 | 看容器是否停了，或配置、应用模式有没有改成功 |
| `OPERATION_UNCERTAIN` | 上一次注入或重置的结果没记清 | 看环境实际状态，再重置 |
| `EVIDENCE_CONFLICT` | 模型引用了不存在的证据，或截图和探针冲突且探针没看到故障 | 看证据列表；图片不能单独当恢复依据 |
| `EVIDENCE_INSUFFICIENT` | 补采后仍没有该场景的故障证据 | 先重置，确认基线后再注入 |
| `PROBE_UNAVAILABLE` | 复测时探针程序自己失败 | 看环境页，不要把这次记成已恢复 |
| `WORKFLOW_ERROR` | 流程节点出现未预期的异常 | 看 `data/backend.log`，再重置 |
| `DOCKER_COMMAND_FAILED` | Docker 命令非零退出 | 详情里有退出码；看 Docker Desktop 和 `default` context |
| `UNSUPPORTED_ATTACHMENT` | 不是 PNG、JPEG、WebP | 换格式再传 |
| `INVALID_ATTACHMENT` | Base64 不合法或内容为空 | 重新编码图片 |
| `ATTACHMENT_TOO_LARGE` | 超过 5MB | 换一张更小的图 |
| `VISION_UNAVAILABLE` | 视觉模型超时或返回异常 | 查 `VISION_*` 和网络 |
| `VISION_INVALID_RESPONSE` | 视觉模型的 JSON 对不上观测契约 | 重传一次；仍失败就不要把这张图当证据 |
| `EVALUATION_ATTACHMENT_NOT_FOUND` | 评测引用的截图编号不存在 | 重新上传，用新的 `id` |
| `EVALUATION_ATTACHMENT_UNAVAILABLE` | 评测时视觉服务不可用 | 同 `VISION_UNAVAILABLE` |
| `SCHEMA_VERSION_MISMATCH` | `data/platform.sqlite3` 的版本不是 0、1、2、3、4 | 不要拿别的版本的库来开。新环境可以移走这个文件重新开始，历史工单会没有 |
| `TWIN_UNAVAILABLE` | 影子没起来，或双侧注入时影子失败 | 工作台旧场景仍可走；编译器双侧注入需要影子。不要声称做过试修 |
| `TWIN_BUSY` | 影子锁被另一场试修占用 | 等当前试修结束 |
| `TWIN_DIVERGENCE` | 两界探针不一致 | 该配方不能用来宣传预测证书 |
| `RECIPE_INVALID` | 配方 DSL 或编号不对 | 用 `/compiler` 里列出的 `rec_` 编号 |
| `RECIPE_NOT_CALIBRATED` | 未见评测抽到了未校准配方 | 先在影子里校准，或换一条 |
| `HOLDOUT_FORBIDDEN_IN_LAB` | 想在工作台注入 holdout | 这是评测考题，换 seen 或用评测页 |
| `SEEN_FORBIDDEN_IN_UNSEEN` | 未见评测抽到了 seen | 不要指定 seen 编号 |
| `CALIBRATION_DIRTY` | 校准后影子回不了基线 | 配方不得进 holdout，先查拆除 |
| `PRIMITIVE_UNSUPPORTED` | 例如没有 NET_ADMIN | 环境不支持这条原语，显式失败 |
| `COMPILER_VERSION_MISMATCH` | holdout 和当前枚举器不对版 | 不要手改 `knowledge/compiler/holdout.json` |
| `NOT_FOUND` | 工单或评测记录不存在 | 核对编号 |

诊断契约拒绝时，工单详情的 `error.details.raw_output` 里会留下模型原文的前一段，用来判断是格式问题还是内容问题。

## 21. 数据放在哪里

| 路径 | 内容 |
| --- | --- |
| `data/platform.sqlite3` | 工单、审计、评测、配方、影子试修。当前结构版本是 4，启动时会从 0、1、2、3 升级。版本只升不降，太新的库会被拒绝启动 |
| `data/platform.lock` | API 单实例锁。锁还在时，第二个 API 起不来 |
| `data/checkpoints.sqlite3` | 工作流检查点。批准能在 API 重启后续上，靠的是它 |
| `data/backend.log`、`data/frontend.log` | 双击启动时的进程日志 |
| `data/attachments/` | 上传的截图，按内容哈希命名 |
| `data/evaluation/` | 评测脚本写出的报告 |
| `data/acceptance/` | 验收脚本的原始响应 |
| `.env` | 本机密钥和口令，不要提交 |
| `.tools/` | 双击脚本下载的 Python 和 Node，不要提交 |

不要靠删除数据库来「把故障恢复」。那会丢掉历史，也不会按重置流程把 Nginx 配置和应用模式改回去。恢复环境用环境页的重置。

`data/` 在 `.gitignore` 里。把整个项目目录打成压缩包时，忽略规则不会自动生效，压缩前确认没有把 `.env` 和 `data/` 打进去。

## 22. 出了问题先看哪里

页面打不开：

- 双击窗口是否还在。关掉窗口会停掉 5173 和 8000。
- 若日志里写着拿不到锁，说明已经有一个 API 占着 `data/platform.lock`。先关掉上一次的演示窗口。
- 端口是不是被上一次演示占着。脚本会直接说明 8000 或 5173 被占用。
- 看 `data/frontend.log`。

注入按钮不可用：

- 环境页的基线是不是全过。
- 是不是还有一张未结束的工单，或评测还在跑。
- 右上角是不是「只读」。只读表示当前页面没有令牌。

诊断一直不动或很快变成流程异常：

- 打开 <http://127.0.0.1:5050/healthz>，Holmes 应该返回成功。
- `docker --context default ps` 里 Holmes 容器应该是 healthy。
- 模型名、API Base 和 `OPENAI_API_KEY` 要和 Holmes 容器里的环境一致。改了 `.env` 要重建 Holmes 容器。
- `HOLMES_API_KEY` 要和平台 `.env`、Holmes 容器一致。它错了会是认证失败，不是模型答错。
- 规划失败时单独看 `PLANNER_URL` 是否以 `/v1` 结尾、`PLANNER_MODEL` 和 `PLANNER_API_KEY`。
- 工作台在探针已经证实故障时，会改走注册动作并停在等待批准。若连这个都没有，说明探针没证实故障，或者进程还是旧代码。重启演示窗口后再注入一张新工单。

批准没有反应：

- 等状态变成等待人工审批再点。检查点没好时会提示稍后再试。
- 不要对旧的 `plan_id` 重复批准。第二轮必须用新编号。

复测通过了但没有弹出对比卡：

- 只有「这一页上等来的」稳定通过会自动弹。刷新进来的历史成功工单要用「查看修复对比」。
- 窗口标了恢复不稳定时不弹。

评测触发失败：

- 工作台若占着环境，先结束或重置。
- C 臂先传截图。
- 看汇总里被剔除的超限和错误，不要把它们算进正确率。

Docker 命令跑到了错误的机器：

- `docker context show` 应是 `default`。
- 新开一个没有 `DOCKER_HOST` 的终端，或直接用双击脚本。

## 23. 不要做的事

- 不要把 `.env`、管理员令牌、数据库密码或模型密钥提交、贴到工单备注、或写进截图。
- 不要对隔离容器执行仓库没有登记的 docker 命令来「帮忙修」。这样审计对不上。重置和白名单动作会把环境收回已知状态。
- 不要把测试夹具或 `TEST/MOCK` 工单写成真实成绩。
- 不要在评测视图之外的材料里，把真值场景名说成模型自己看过的输入。模型上下文里故意没有场景名。
- 不要删除失败工单后再报一个全绿的结果。失败记录是结果的一部分。
- 不要把 holdout 配方拿到工作台彩排。那是评测考题。
- 不要把未见组合题塞回六个根因枚举去报一个虚高正确率。

## 25. 故障编译器与随机注入

没读过设计文档也可以按这一节做完一次随机注入。

1. 贴好管理员令牌。环境页真环境四个容器要绿。影子最好也在；双侧注入需要影子。
2. 打开「故障编译器」。上面能看到枚举池数量和冻结的 holdout 数量。holdout 默认折叠，写着「评测用，勿在演示注入」。
3. 回到「故障实验」，点「抽一条 seen 注入」，或在旁边粘贴 `rec_…` 指定配方。确认框只说可观测症状，不会把考题原语念出来。
4. 若提示 `HOLDOUT_FORBIDDEN_IN_LAB`，说明这是评测考题，换一条或用随机 seen。
5. 工单标题是配方症状，不是六个根因枚举。诊断、规划之后先看「影子预测」：可能写「这次还不能完全恢复」。
6. 你仍然只批准真环境那一次。批准后复测会生成证书：预测和实测逐探针对照。对不上记预测失败，不以影子改写真环境结论。
7. 环境页「重置演示环境」会同时收回两界。

也可以在编译器页粘贴 `rec_…` 再注入。不要把 holdout 当演示彩排。

## 26. 未见故障评测

未见故障和工作台、普通盲诊都分开。

1. 打开「盲诊评测」，样本组选「未见故障（holdout）」。
2. 选 A 或 A+B。不要选 R。R 臂要在影子里执行目录动作，不能进盲诊。
3. 点「触发实验」。服务端只抽 holdout。模型上下文里没有配方编号、原语和期望签名。
4. 汇总里的「未见故障」是单独分母：签名覆盖、精确率、因漂移剔除的条数、弱解析条数。不要把它和上面的根因正确率合成一句「模型很准」。缺失 `failing_check_ids` 时会弱解析并标明。
5. 无令牌时摘要和列表都不会出现配方原语。切换评测视图才看得到真值，而且需要管理员令牌。

脚本：

```bash
./.venv/bin/python scripts/run_unseen_evaluation.py
./.venv/bin/python scripts/check_holdout.py
```

`check_holdout.py` 用来确认冻结文件没被无意改掉。不要手改 `knowledge/compiler/holdout.json`。

影子验收（需要 Docker 且八个容器都在）：

```bash
./.venv/bin/python scripts/run_twin_acceptance.py
```

没有 Docker 时这条脚本退出码 2，不算平台崩溃。
